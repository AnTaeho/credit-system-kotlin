# ADR-004 — worker batch-size 20 → 3

- 날짜: 2026-08-20
- 저장소: JAVA (`../credit_system`)
- 커밋: `a2eef5a`(측정, 10:08:10) → `8f54e13`(적용, 10:08:26)

**주: 이 문서집에서 "결과" 칸이 실제 측정치로 채워지는 유일한 ADR 이다.**
나머지 여섯은 전부 "미측정" 아니면 문서 인용이다. 그 대비가 이 프로젝트의 현재 상태를 말한다.

## 상황

ADR-002 로 폴링 잡큐가 된 뒤 `app.worker.batch-size: 20` 이라는 값이 남았는데, 그 값에 근거가 없었다.

> **재려던 것**: `app.worker.batch-size: 20`의 근거가 어디에도 없었다. concurrency가 3인데 20을 읽는 게
> 과대 설정인지, job이 빨라질 때를 대비한 보험인지 판단할 데이터가 없었다.

— 출처: JAVA `docs/develop-report.md` "완료: batch-size 실측 (2026-08-20)"

세운 가설은 **틀렸고, 틀렸다는 기록이 그대로 남아 있다.**

> **세웠던 가설 — 틀렸다**: 슬롯이 비는 속도가 `concurrency / job소요시간`이므로 폴러가 뒤처지지 않으려면
> `batch-size >= concurrency × (폴링주기 / job소요시간)`이어야 한다고 봤다. 이 식대로면 job이 100ms까지
> 빨라질 때 batch-size 15가 필요하고, 20은 합리적 보험이 된다.

— 같은 절

## 결정

`app.worker.batch-size: 20 → 3`(= concurrency). 결론 두 문장을 그대로 옮긴다.

> ... **한 폴링 주기가 나눠줄 수
> 있는 최대치는 batch-size가 아니라 concurrency다.**

> 처리량 상한 = min(concurrency / job소요시간, concurrency / 폴링주기)
>
> batch-size는 이 식에 등장하지 않는다. 필요한 값은 concurrency다.

— 같은 절

`concurrency + 1` 이 아니라 정확히 `concurrency` 인 이유도 측정에서 나왔다.

> 확인 측정에서 `batch-size = 3`이 4와 처리량이 같으면서 읽는 행이 적고 헛도는 UPDATE가 절반이었다.
> 200ms 행에서는 헛도는 UPDATE가 정확히 0이다 — 리스트가 concurrency개면 거부 없이 루프가 자연 종료되어
> 탐침용 왕복 자체가 사라진다. `concurrency + 1`이 아니라 `concurrency`가 답이다.

— 같은 절

적용은 `8f54e13`(3 files, +5/−5) — `application.yml`, `application-test.yml`, README 두 군데 서술.
측정 커밋 `a2eef5a`(`WorkerBatchSizeBenchmark` +265, `BatchSizeResult` +13)가 **16초 먼저** 들어갔다.
순서가 측정 → 적용이라는 사실이 커밋 타임스탬프에 남아 있다.

## 대안

- **batch-size 를 20 그대로 두기** — 측정으로 기각. 처리량은 같고 읽기 비용만 늘어난다.
  "batch-size 4에서 20으로 가면 읽는 양이 4.6배가 되고 처리량은 소수점도 안 움직인다."
- **batch-size 를 키워 처리량을 올리기**(원래 가설) — 측정으로 기각. 막고 있는 것이 batch-size 가 아니었다.
- **폴링 주기 / concurrency 를 돌리기** — 기각이 아니라 **올바른 노브로 지목**됐다.
  "job이 빨라질 때 돌려야 할 노브는 **폴링 주기**(또는 concurrency)다. 예를 들어 30 TPS가
  필요하면 `폴링주기 <= concurrency / 30 = 100ms`로 내려야 한다." 다만 이 축은 이번에 돌리지 않았다.

## 결과

**측정으로 확인됨(벤치마크 기준).** 다만 프로덕션 트래픽 측정이 아니라
`WorkerBatchSizeBenchmark` 위에서의 확인 측정이라는 점을 분명히 둔다.

- batch-size 3 은 4·5·8·20 과 **처리량이 같다**(1000ms 행 2.8 TPS, 200ms 행 5.6 TPS).
- 읽기 비용은 낮다 — 1000ms 행에서 완료 1건당 읽은 행이 batch-size 4 의 2.8 대비 **2.1**,
  20 의 13.8 대비 6분의 1 수준이다.
- 헛도는 UPDATE 는 1000ms 행에서 4·5 의 1.4 대비 **0.7**, 200ms 행에서는 **정확히 0**.
- 실측 TPS 천장 5.8 = `concurrency / 폴링주기 = 3 / 0.5초` 의 실측값. 유휴율 6.7% 가 포화 지점.

**한계 — 그대로 옮긴다.**

> **측정 범위의 한계**: 이 결론은 **단일 인스턴스** 전제다. 다중 인스턴스에서는 `claim` 실패가 `continue`이므로
> 남이 선점한 job을 건너뛰고 더 뒤까지 훑을 수 있어야 하고, 그때 batch-size는 처리량이 아니라 경합 헤드룸으로
> 기능한다. 그 축은 측정하지 않았다(백로그 #9와 같은 이유로 범위 밖). 인스턴스를 늘리면 batch-size 3은
> 재검토 대상이다.

— 같은 절
