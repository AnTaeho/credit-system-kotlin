# 01. 성능·안정성 요구서

> 본 요구서는 초기 구현 이후 정식화(retrofit)되었으며, 이후 단계부터는 요구서가 구현을 선행한다.

작성 시점: 2026-09-22. 작성 브랜치: `req-retrofit`(tip `e2a54b4`).

이 문서는 **목표**를 선언한다. 목표와 사실을 섞지 않기 위해 규율 두 가지를 둔다.

1. 모든 PERF·INV 항목의 **현재 상태** 칸에는 **미측정 / 통과 / 실패** 셋 중 하나만 쓴다.
   "예상 통과" 같은 말은 칸이 아니라 각주에 쓴다.
2. 모든 현재 상태에는 `docs/00-inventory.md`(이하 **인벤토리**)의 절 번호 또는
   파일:메서드 인용을 붙인다. 인벤토리에 없는 사실은 코드를 열어 확인하고 근거를 단다.

산술은 식을 보여준다. 측정하지 않은 값을 결과처럼 쓰지 않는다.

## 1. 서비스 가정 (Assumptions)

### 1-1. 이 표는 설계 훈련용 가상 시나리오다

아래 규모는 **이 프로젝트의 실제 운영 목표가 아니다.** 실제 목표는
`docs/roadmap.md` 결정 8("조직은 개인 사용자 한 명이다", 2026-09-19)과
결정 13("서버는 1대", 2026-09-19)에 따라 **개인 사용자 대상, 앱 서버 1대**다.
DAU 100만 규모는 "이 설계가 어디서 깨지는가"를 논증하기 위한 가상 부하이며,
그 논증의 결론은 2절 Tier B·C 와 Phase 2 의 일이다.

| 항목 | 값 | 근거 구분 |
|---|---|---|
| DAU | 1,000,000 | **추정.** 국내 카테고리 상위권 앱 수준 |
| 1인당 일 쓰기(크레딧 소비) | 10회 | **가정** |
| 1인당 일 조회 | 30회 | **가정**(쓰기의 3배) |
| 일 쓰기 | 10,000,000 | **산술** 1,000,000 × 10 |
| 평균 쓰기 RPS | ≈ 116 | **산술** 10,000,000 ÷ 86,400 = 115.7 |
| 일 조회 | 30,000,000 | **산술** 1,000,000 × 30 |
| 평균 조회 RPS | ≈ 347 | **산술** 30,000,000 ÷ 86,400 = 347.2 |
| 일상 피크 배수 | ×8 | **가정** |
| 설계 목표 피크 쓰기 | ≈ 1,000 RPS | **산술** 115.7 × 8 = 925.6 |
| 이벤트 피크 배수 | ×25 | **가정** |
| 생존 목표 피크 쓰기 | ≈ 3,000 RPS | **산술** 115.7 × 25 = 2,892.5 |
| 조회 피크 | ≈ 2,800 / 8,700 RPS | **산술** 347.2 × 8 = 2,777.6 / 347.2 × 25 = 8,680 |
| 외부 API 지연 | p50 200ms / p99 2s / timeout 5s | **가정.** 현재 스텁은 지연 3~7초·timeout 20초라 **다르다**(인벤토리 2-1) |
| 외부 API 실패율 | 평시 0.1%, 장애 시 100%(최대 10분) | **가정.** 현재 스텁은 `app.stub.failure-rate: 0.3`(인벤토리 2-1) |

외부 API 가정과 현재 스텁이 다른 것은 결함이 아니다. 스텁은 장애 주입 도구로 쓰려고
일부러 느리고 자주 실패하게 맞춰 놓은 값이다(`application.yml` 의 `app.stub.*`).
그래서 부하 측정은 아래 1-3 의 두 프로파일로 나눈다.

### 1-2. 초안을 정정한 두 곳

**정정 1 — 원장 행 증가는 초안의 두 배다.**

초안은 "일 1천만 행, 연 36억"이었다. 이 시스템은 **job 하나가 원장 2행**을 만든다.

- 성공 경로: `HOLD`(−100) + `CONFIRM`(0) = 2행 (인벤토리 3-1 S1·S5, 3-3 부호 규약)
- 최종 실패 경로: `HOLD`(−100) + `REFUND`(+100) = 2행 (인벤토리 3-1 S6)
- 재시도해도 `HOLD` 는 늘지 않는다. `retry` 는 `incrementAttemptForRetry` 로
  `attemptNo` 만 올릴 뿐 원장을 쓰지 않는다(인벤토리 3-1 S6 3번).

따라서:

```
일 원장 행 = 10,000,000 job × 2 = 20,000,000 행
연 원장 행 = 20,000,000 × 365   = 7,300,000,000 행 ≈ 73억 행
```

운영자 지급(`ADMIN_GRANT`)·충전 원장은 이 산술에 넣지 않았다(인벤토리 3-1 지급 흐름).
이 정정은 PERF-04 와 Tier C 에 직접 걸린다.

**정정 2 — Tier A 500 RPS 는 DAU 54만에 해당한다.**

초안은 "DAU 40~50만"이었다. 1절의 가정(일상 피크 ×8, 1인당 일 쓰기 10회)으로 환산하면:

```
평균 쓰기 RPS = 500 ÷ 8       = 62.5
일 쓰기       = 62.5 × 86,400 = 5,400,000
DAU           = 5,400,000 ÷ 10 = 540,000
```

즉 **DAU 54만**이다. 뒤집어 보면 DAU 100만 기준으로는

```
500 ÷ 115.7 = 4.32 → 평균의 ×4.3 피크
```

에 해당한다. 설계 목표 피크(×8, 926 RPS)에는 못 미치고, 평균(116 RPS)의 4배는 넘는다.

### 1-3. 사용자와 합의한 것 (2026-09-22 네 가지, 2026-09-23 두 가지)

**합의 1 — Tier A 의 "쓰기 RPS"는 접수 기준이다.**
`POST /api/jobs` 가 HTTP 응답을 돌려주기까지를 센다. 즉 TX-1(`HoldService.requestGeneration`,
인벤토리 2-1 트랜잭션 경계)의 왕복이다. 워커가 실제로 외부 호출을 끝내는 속도는
이 숫자와 무관하며 **PERF-07 로 분리**한다.

**합의 2 — 부하 시 스텁은 두 프로파일로 각각 잰다.**

| 프로파일 | 설정 | 무엇을 재는가 |
|---|---|---|
| (a) 운영 기본값 | `failure-rate: 0.3`, 지연 3~7초, `timeout-seconds: 20` (현재 `application.yml`) | **지금 이 서비스**가 어떻게 동작하는가 |
| (b) 부하용 | 지연을 짧게 낮춘 값 | **크레딧 시스템 자체**의 한계(외부 지연에 가리지 않은 접수·DB 경로) |

(b) 의 구체적인 값은 Phase 3 에서 정한다. 두 프로파일의 접수 지연이 같게 나오면
그것이 PERF-03 의 근거가 된다.

**합의 3 — INV-02 의 공식은 현행 `balance == initialBalance + Σledger` 다.**
`docs/roadmap.md` 결정 2("원장이 유일한 진실이다", 2026-09-10)는 `initialBalance` 를 없애고
공식을 `잔액 − Σ원장`으로 바꾸자고 하지만 **미구현**이다(인벤토리 3-3: 컬럼도 공식도
그대로이고 V1~V5 어디에도 제거 문장이 없다). 이 요구서는 현행 공식을 검증 대상으로 쓰고,
공식 교체는 **Phase 2 의 gap** 으로 넘긴다.

**합의 4 — Tier A 실측 런타임은 호스트 JVM(OpenJDK 26, 26+35-2893)이다.**
DB·Redis 만 Docker 컨테이너로 띄운다(인벤토리 5절). 컨테이너 런타임
(`eclipse-temurin:17-jre`, `Dockerfile`)에서의 측정은 하지 않는다. 인벤토리 5절이
"Tier A 실측을 어느 런타임에서 할지는 미결"이라고 남긴 항목을 여기서 닫는다.

주의: 앱 JVM 과 DB 는 같은 물리 머신(Apple M4 10코어·16GiB)을 나눠 쓴다.
Docker VM 에 8 CPU / 3.83GiB 가 할당돼 있으므로, 부하 중 앱과 DB 는 같은 CPU 를 두고
경쟁한다(인벤토리 5절). Tier A 결과는 "CPU 를 나눠 쓰는 1대에서의 값"이라고 읽어야 한다.

**합의 5 (2026-09-23) — `ledger_entries` 는 삽입만 되는 테이블로 만든다.**
INV-06 을 강제할 DB 장치를 두는 것이 이 작업의 범위 안이다. 수단(트리거 / 권한 회수 / 둘 다)은
Phase 2 에서 고르고, 테스트를 먼저 실패시킨 뒤 장치를 붙인다. 근거와 수단 비교는 4-5.

**합의 6 (2026-09-23) — 부하에서 인증을 우회하지 않는다.**
인증은 스펙의 일부다. 한 번의 요청이 실제 서비스 요청과 같은 구조로 돌고, **그 구조 안에서**
성능 목표에 닿는 것이 목표다. 따라서 PERF-01·PERF-02 의 목표치는 인증 트랜잭션을 포함한
요청 전체에 대한 값이다. 상세는 1-4.

### 1-4. 부하 스크립트의 신원 가정

모든 API 에 인증이 걸려 있다(인벤토리 2-1 인증, `SecurityRulesTest` 11건).
부하는 **개발 로그인 헤더**로 친다고 가정한다.

- 헤더 `X-Dev-User: <email>`
- `app.auth.dev-login.enabled: true`(기본 `false`, `application-local.yml` 에서 켠다)
- 대상 이메일이 `app.auth.allowed-emails` 안에 있어야 한다
- prod 프로필에서 이 조합은 `AuthStartupGuard` 가 기동을 거부한다(인벤토리 2-1)

**이 경로는 요청마다 DB 를 친다 — 확인된 사실이다.**
`DevLoginFilter.doFilterInternal` 이 요청마다 `DevLoginAuthenticator.authenticate` 를 부르고,
그것이 `UserAccountProvisioner.provisionDevUser(email)` 를 부른다. 인증 결과를 세션에
저장하지 않고 **요청 하나에만** 건다(`DevLoginFilter` KDoc). `provisionDevUser` 는
`TransactionTemplate` 안에서 `userRepository.findByEmail(normalized)` SELECT 를 한 번 돌리고,
없을 때만 `saveAndFlush` 로 INSERT 한다 — 즉 **첫 요청만 INSERT, 이후는 매 요청 SELECT 1회**다
(`auth/login/UserAccountProvisioner.kt:provisionDevUser`).

따라서 접수 1건의 실제 모양은 이렇다:

```
요청 1건 = [인증 트랜잭션: SELECT users] → [TX-1: idem SELECT/INSERT + 잔액 UPDATE + jobs INSERT + attachJobId + ledger INSERT]
         = DB 트랜잭션 2개 순차, 커넥션 획득 2회, 커밋 2회
```

커밋마다 fsync 가 일어난다(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, 인벤토리 5절).

**2026-09-23 사용자 확정 — 인증을 우회하지 않는다.** 인증은 이 서비스의 스펙이고,
한 번의 요청은 **실제 서비스 요청과 같은 구조**로 돌아야 한다. 따라서

- 부하 전용 인증 우회 경로를 만들지 않는다.
- PERF-01·PERF-02 의 목표치(p50 < 20ms, p99 < 100ms / p99 < 30ms)는
  **인증 트랜잭션을 포함한 요청 전체**에 대한 목표다. 커넥션 예산·fsync 횟수도
  요청당 2회 기준으로 잡는다(2-1).
- 이 구조 안에서 목표에 닿지 못하면, 그것은 측정 방법의 결함이 아니라
  **이 구조가 목표를 못 내는 것**이고 그대로 실패로 기록한다.

다만 원인을 갈라 보기 위해 인증 구간과 접수 구간의 지연을 **나눠 기록**한다
(목표 판정은 합계로, 병목 규명은 구간별로 — 2-2 의 Tier B 관측 항목과 같은 이유다).
운영에서 쓰는 구글 OIDC 로그인은 세션 쿠키를 쓰므로 요청당 DB 조회가 이 경로와 다르다.
**부하가 재는 것은 개발 로그인 경로**라는 사실을 결과 파일에 함께 적는다.

### 1-5. 부하 실행의 선행조건 — 크레딧 시드

이 항목이 빠지면 결과가 오염된다. `app.generation.cost: 100` 이므로:

| 시나리오 | 소모 크레딧 | 식 |
|---|---|---|
| Tier A (500 RPS × 10분) | 30,000,000 | 500 × 600 × 100 |
| PERF-06 (3,000 RPS × 10분) | 180,000,000 | 3,000 × 600 × 100 |
| PERF-05 핫 계정(25 RPS × 10분) | 1,500,000 | 25 × 600 × 100 |

운영자 지급 1회 상한은 `app.admin.max-grant-amount: 1000000`(`application.yml`)이다.
Tier A 하나만 해도 **지급 API 를 최소 30회** 부르거나 사용자를 분산해야 한다.
시드가 모자라면 `InsufficientBalanceException` 이 나는데 그것은 HTTP **409
`INSUFFICIENT_BALANCE`** 로 돌아온다(`global/exception/GlobalExceptionHandler.kt:handleInsufficientBalance`
→ `conflict(...)` → `HttpStatus.CONFLICT`). **이 409 는 부하 결과가 아니라 시드 실패다.**
k6 스크립트는 이 코드를 오류율에 섞지 말고 별도로 세야 한다.

## 2. 용량 등급 (Tier A / B / C)

### 2-1. Tier A — 로컬 실측 목표

| 항목 | 값 |
|---|---|
| 접수 처리량 | 500 RPS 지속 |
| 지속 시간 | 10분 |
| 지연 | p99 < 100ms |
| 오류율 | 0% (1-5 의 시드 실패 409 는 제외) |
| 실측 환경 | 호스트 JVM OpenJDK 26, MySQL 8.4·Redis 7 컨테이너, Apple M4 10코어/16GiB, Docker VM 8 CPU/3.83GiB (인벤토리 5절, 합의 4) |
| 부하 도구 | k6 1.6.0 (호스트 설치됨, 인벤토리 4-3) |
| 신원 | `X-Dev-User` 헤더 (1-4) |

DAU 환산은 1-2 의 정정 2 — **DAU 54만**, 또는 DAU 100만의 ×4.3 피크.

**커넥션 예산 산술.** HikariCP 설정이 없어 최대 10 이다(인벤토리 5절).

```
커넥션 1개가 감당해야 하는 초당 요청 = 500 ÷ 10 = 50 건/s
→ 요청 하나가 커넥션을 쥐고 있어도 되는 시간 = 1,000ms ÷ 50 = 20ms
```

이 20ms 는 **1-4 의 두 트랜잭션(인증 + TX-1) 합계 예산**이다. 커밋 2회의 fsync 가
여기 들어간다. 이 예산을 못 지키면 커넥션 대기가 지연으로 나타난다 — Tier A 가 깨질 때
가장 먼저 볼 곳이다.

### 2-2. Tier B — 설계 보증(DAU 100만)

**지금은 외삽할 근거가 없다.** 로컬 1대 실측에서 DAU 100만을 논증하려면 어떤 자원이
어디서 먼저 포화하는지를 알아야 하는데, 그 관측이 저장소에 없다(인벤토리 4-3:
부하·성능 테스트 없음). 그러므로 이 절은 목표 수치가 아니라
**"무엇을 측정해야 외삽이 가능한가"** 만 적는다.

아래 목록이 **Phase 3 부하 결과 파일의 필수 칸**이 된다. 하나라도 비면 Tier B 논증을
시작하지 않는다.

| 관측 항목 | 어떻게 | 왜 필요한가 |
|---|---|---|
| 앱 JVM CPU | 프로세스 CPU 또는 actuator `process.cpu.usage` | 앱이 먼저 포화하는지 |
| DB 컨테이너 CPU | `docker stats` | DB 가 먼저 포화하는지. 앱과 CPU 를 나눠 쓰므로 둘을 같이 봐야 한다(인벤토리 5절) |
| HikariCP 커넥션 대기 | actuator prometheus 의 `hikaricp.connections.pending` 등 — **노출 여부 미확인** | 2-1 의 20ms 예산이 깨지는지. 노출되지 않으면 Phase 3 에서 노출 방법부터 정한다 |
| MySQL 락 대기 | `SHOW ENGINE INNODB STATUS` 또는 `performance_schema` | 잔액 조건부 UPDATE 가 직렬화되는 지점(PERF-05 와 같은 원인) |
| 디스크 fsync | `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1` 이라 **커밋마다 fsync** (인벤토리 5절) | 쓰기 처리량의 하드 바닥. 요청당 커밋 2회(1-4) |
| 대사 배치의 부하 기여 | 60초마다 도는 `LedgerReconciliationTask` 의 실행 시간 | 부하 중에도 이 배치가 원장을 훑는다(3-3, 2-3 참조) |

### 2-3. Tier C — 설계 한계(DAU 500만+)

구조적 한계 **후보**를 사실로만 나열한다. 어디서 실제로 깨지는지, 무엇으로 바꿀지는

### 3-1. PERF-03 의 이 시스템에서의 해석

`GenerationClient.generate` 는 다섯 트랜잭션 경계(TX-1~TX-5) **어디에도 들어 있지 않다.**
`GenerationJobProcessor.runGeneration` 에는 `@Transactional` 이 없고, 외부 호출은 워커
스레드에서 트랜잭션 밖으로 나간다(인벤토리 2-1 트랜잭션 경계, 3-1 S4).
접수 경로(TX-1)는 외부 호출과 스레드도 트랜잭션도 공유하지 않는다.

즉 **구조적으로 접수 지연이 외부 지연에 영향받지 않아야 한다.** 통과가 예상되지만
측정하지 않았으므로 현재 상태는 미측정이다. 통과하면 그 수치가 hold/confirm 분리
설계(돈을 먼저 묶고 외부 호출은 비동기로)의 정당화 근거가 된다.

### 3-2. PERF-07 의 산술

```
10분간 접수    = 500 RPS × 600초 = 300,000 건
워커 처리 상한 = 0.43 ~ 1.0 건/s  (동시 3 ÷ 건당 3~7초, 인벤토리 2-1)
소진 시간      = 300,000 ÷ 1.0  = 300,000초   ≈ 83시간
                 300,000 ÷ 0.43 = 697,674초  ≈ 194시간
```

전부 **설정값 산술이며 실측이 아니다.** 게다가 이것은 **하한**이다 —
`app.stub.failure-rate: 0.3` 이므로 약 30%가 실패해 재시도로 슬롯을 다시 먹고,
`timeout-seconds: 20` 까지 쓰는 건이 섞이면 상한은 더 내려간다(인벤토리 2-1).

따라서 PERF-07 의 목표는 "다 처리한다"가 될 수 없다. 목표는
**"접수는 계속 성공하고, 적체는 쌓이되 시스템이 깨지지 않으며, 부하가 멈추면 줄어든다"**
이다. 이 격차 자체를 없애는 것(워커 스케일아웃, 접수 제한, 큐 상한)은 Phase 2 의 일이다.

## 4. 불변식 (INV)

각 불변식에는 자동화 테스트가 하나 이상 있어야 한다. 이미 있으면 인용하고,
없으면 "테스트 없음 — Phase 3 에서 작성"이라고 쓴다.

| ID | 조건 | 목표 | 측정 방법 | 현재 상태 |
|---|---|---|---|---|
| **INV-01** | 어떤 동시성·부하에서도 | `users.balance` 가 음수가 되지 않는다 | 기존: `ConcurrentHoldTest`(동시 요청에도 잔액 음수 없음), `UserRepositoryTest`(잔액 부족이면 조건부 UPDATE 가 0행·잔액 불변), `DomainSnapshotTask` 의 음수 잔액 게이지(`DomainSnapshotTaskTest`) | **통과** — 인벤토리 4-2 [^1] |
| **INV-02** | 언제나 | 원장 합계와 잔액이 일치한다 (아래 4-1 의 세 검사) | 4-1 참조. 세 검사 모두 코드에 이미 있다 | **통과** — 인벤토리 4-2 [^2] |
| **INV-03** | 동일 `(userId, idemKey)` 로 N회 요청 | 차감 정확히 1회 **+ 같은 `jobId` 반환** | 기존: `DuplicateIdemKeyTest`, `ConcurrentGrantTest`, `IdempotencyKeyRepositoryTest`(인벤토리 4-2). 부하 중 검증은 4-2 의 k6 주의사항을 지켜야 한다 | **통과** — 인벤토리 4-2 [^3] |
| **INV-04a** | 외부 호출이 성공했든 실패했든, 한 job 에 대해 | **사용자에게서 나가는 돈은 정확히 1회** — 성공이면 hold 1회로 끝나고, 실패면 hold 와 같은 금액이 환불되어 잔액이 원상 | fault injection 으로 C3c·C4 지점에서 프로세스를 죽이고, 재기동 뒤 그 사용자의 잔액과 원장(HOLD 1 + CONFIRM 또는 REFUND 1)을 확인. ### 4-1. INV-02 를 세 검사로 정의한다

| # | 검사 | 구현 | 상태 |
|---|---|---|---|
| (a) | `balance == initialBalance + Σledger` (사용자별) | `ledger/scheduling/LedgerReconciliationTask.kt:isBalanceConsistent`, 데이터는 `LedgerRepository.findBalanceChecksAfter` 가 100건 커서로 공급 (인벤토리 3-3) | 검증됨 — `LedgerReconciliationTaskTest` 7건 |
| (b) | HOLD 원장이 없는 job 0건 | `countJobsWithoutHoldEntry` (`DomainSnapshotTask`) | 검증됨 — `DomainSnapshotTaskTest` |
| (c) | 미정산 종결 job 0건 | `countUnsettledTerminalJobs` (`DomainSnapshotTask`) | 검증됨 — `DomainSnapshotTaskTest` |

공식 (a) 는 합의 3 에 따라 **현행 공식**이다. `initialBalance` 제거는 Phase 2 의 gap 이다.

**측정 도구 gap — 부하 직후 대사를 돌릴 수단이 없다.**
`LedgerReconciliationTask.reconcile` 은 `fixedDelay 60000ms` 로만 돈다(인벤토리 2-1 스케줄러 표).
수동 트리거 엔드포인트도, 테스트 훅도 없다. 즉 지금은
"부하를 멈추고 → 대사를 즉시 돌려 → 0건을 확인한다"가 **불가능**하고,
최대 60초를 기다리며 그 사이 스케줄러가 돌았는지를 로그·지표로 추정해야 한다.
**Phase 3 에서 트리거 수단을 만들어야 한다.**

### 4-2. INV-03 의 경계 — k6 가 세면 안 되는 응답

첫 요청이 `idempotency_keys` 행을 INSERT 한 뒤 `attachJobId` 를 끝내기 전에 같은 키로
두 번째 요청이 들어오면, `HoldService.resolveDuplicateRequest` 가
`DuplicateRequestInProgressException` 을 던진다(인벤토리 3-1 S1 2번).
이것은 **불변식을 지키는 정상 동작이지 실패가 아니다** — 차감이 두 번 일어나는 대신
두 번째 요청을 거절한 것이다.

이 예외는 HTTP **409 CONFLICT**, 본문 코드 **`DUPLICATE_IN_PROGRESS`** 로 나간다
(`global/exception/GlobalExceptionHandler.kt:handleDuplicateInProgress` →
`conflict(...)` → `HttpStatus.CONFLICT`). 같은 코드가 DB 유니크 제약에 걸린 경우에도
쓰인다(`handleDataIntegrityViolation`).

**k6 재시도 스크립트가 409 `DUPLICATE_IN_PROGRESS` 를 실패로 세면 결과가 오염된다.**
1-5 의 409 `INSUFFICIENT_BALANCE`(시드 실패)와도 코드로 구분해야 한다.
오류율 집계는 HTTP 상태가 아니라 본문의 `code` 로 분류한다.

### 4-3. INV-04 를 왜 둘로 쪼갰나 (2026-09-23 확정)

**초안의 INV-04("정확히 1회 과금")는 이 시스템의 경계에서 달성할 수 없다.**
외부 호출의 중복을 막는 유일한 수단은 외부가 멱등키를 받아 주는 것인데,
**이 프로젝트가 가정하는 외부 API(지연 3~7초)는 멱등키를 지원하지 않는다**
(2026-09-23 사용자 확정. 실제 API 를 붙이지 않으므로 이것은 조사 결과가 아니라 가정이다).
멱등키가 없으면 C3c 는 원리적으로 닫히지 않는다 — 호출이 닿았는지를 알 방법이 없기 때문이다.

달성 불가능한 불변식을 그대로 두면 요구서가 거짓말을 한다. 그래서 둘로 나눈다.

- **INV-04a — 불변식.** 사용자에게서 나가는 돈은 정확히 1회다. 이것은 달성 가능하고
  이미 단건 경로가 통과한다. 크래시 주입 검증만 남았다.
- **INV-04b — 지표.** 외부 호출 중복은 **상한 있는 손실**이다. 막을 수 없으니 **세고 묶는다** —
  상한은 job 당 `app.generation.max-attempts: 3` 회이고, 발생률을 지표로 본다.

이 분할은 `docs/roadmap.md` 결정 12(2026-09-19, "재시도로 원가가 여러 번 나가도 사용자는
한 번만 낸다 … 이 원가는 운영자 손실이다")와 일치한다. 설계 문서 1-2 가 적은 충돌은
이 분할로 닫힌다. 외부가 멱등키를 지원하는 API 로 바뀌면 INV-04b 는 다시 불변식이 될 수 있고,
그때 필요한 설계는 `docs/02-design.md` 1-2 에 그대로 남겨 둔다.

위반 경로는 코드에 있다. 인벤토리 3-2 의 두 행이다.

| 경로 | 무슨 일이 일어나는가 |
|---|---|
| **C3c** | 외부 호출이 전송된 뒤 응답 전에 프로세스가 죽는다. 부작용이 일어났는지를 **시스템이 알 수 없다** — 호출이 닿았는지를 기록하는 자리가 코드에 없고 남는 것은 로그뿐 |
| **C4** | 외부 호출 성공 직후, `confirm` 전에 죽는다. `resultUrl` 은 DB 에 없다. heartbeat 만료로 약 10~15초 뒤 FAILED → 재시도 → **외부 호출이 중복 발생**. 상한 3회를 소진하면 `finalRefund` |

**손실을 둘로 나눠야 한다.**

- **사용자 손실: 없다.** 잔액은 `finalRefund` 로 원상 복구되고 REFUND 원장이 남는다
  (인벤토리 3-1 S6). 사용자가 돈을 잃는 경로가 아니다.
- **서비스 손실: 있다.** 서비스가 문 외부 호출의 원가는 회수되지 않는다. 중복 호출이면
  두 번 물고, 이미 만들어진 결과 URL 은 유실된다(인벤토리 3-2 C4 근거,
  JAVA `docs/db-job-queue-refactor.md` 5번 항목이 Java 시절에 같은 내용을 적어 뒀다).
  `docs/roadmap.md` 결정 11 이 "실패 전액 환불과 손실 지표"를 이미 열린 항목으로 두고 있다.

이 항목이 **Phase 2 의 2단계 커밋·외부 호출 멱등키 설계의 근거**가 된다.
자동화 테스트도 없다 — `GenerationJobProcessorTest` 의 "결과 반영이 실패해도 FAILED 로
바꾸지 않고 PROCESSING 을 유지한다"는 `confirm` 이 **예외를 던지는** 경우이고 프로세스
사망이 아니다(인벤토리 4-3).

### 4-4. INV-05 — 목표 T=10분 vs 현재 설정의 최악 경로

설정값(`application.yml`)과 회수 로직(`DeadJobRecoveryTask.kt:scan`)으로 계산한다.

**최악 경로는 hang 이다**(`app.stub.hang: true`, 인벤토리 3-2 C7).
멈춘 워커의 heartbeat 갱신 스레드는 계속 살아 있어 ZSET score 를 5초마다 밀어 올린다.
그래서 `findExpiredAttempts` 에는 영영 안 잡히고, 정체 스캔도 LIVE 를 보고 60초에는
건너뛴다. `updatedAt < now − absolute-timeout-seconds(300)` 이 될 때만 `HARD_CAP` 으로 내린다.

한 번의 scan 안에서 2단계(`markStalledJobsAsFailed`)가 FAILED 로 바꾸고 이어서
3단계(`retryOrRefundFailedJobs`)가 그 job 을 집으므로, 회수와 재투입은 같은 주기에 끝난다
(`DeadJobRecoveryTask.kt:scan` — 세 단계를 순서대로 부른다).

```
시도 0: HARD_CAP 300초  + scan 대기 ≤5초  → FAILED, 같은 주기에 retry (nextAttemptAt = +10초)
        backoff 10초 + dispatch 대기 ≤0.5초
시도 1: HARD_CAP 300초  + scan 대기 ≤5초  → FAILED, 같은 주기에 retry (nextAttemptAt = +40초)
        backoff 40초 + dispatch 대기 ≤0.5초
시도 2: HARD_CAP 300초  + scan 대기 ≤5초  → FAILED, attemptNo+1 = 3 이므로 finalRefund

합 = 3 × absolute-timeout-seconds(300)
   + backoff base-seconds(10) + base × multiplier(40)
   + 3 × dead-job-scan-interval(≤5)
   + 2 × worker-interval(≤0.5)
   = 900 + 50 + (0~15) + (0~1)
   = 950 ~ 966초  ≈ 15.8 ~ 16.1분
```

설정 출처: `app.processing.absolute-timeout-seconds: 300`,
`app.generation.retry-backoff.base-seconds: 10` / `multiplier: 4`,
`app.generation.max-attempts: 3`(그래서 쓰이는 backoff 는 10초·40초 두 번),
`app.scheduling.dead-job-scan-interval-millis:5000`·`app.scheduling.worker-interval-millis:500`
(두 키는 **yml 에 없고 `@Scheduled` 애너테이션 기본값**이다 — 인벤토리 2-1 스케줄러 표).

**결론: 현재 설정으로 T = 10분은 구조적으로 불가능하다.** 최악 ≈ 16.1분이다.

**대비 — hang 이 아닌 경우는 T=10분 안에 들어온다.**

```
합 = 3 × generation.timeout-seconds(20) + 10 + 40 + 3 × scan(≤5) + 2 × dispatch(≤0.5)
   = 60 + 50 + 15 + 1 = 126초 ≈ 2.1분
```

즉 T=10분이 깨지는 것은 **hang(응답도 타임아웃도 없는 멈춤) 경로에서만**이다.

**주의 — hang job 하나가 워커 풀 전체를 죽인다. 그 뒤의 T 에는 상한이 없다.**

hang 은 워커 슬롯을 반환하지 않는다(인벤토리 3-2 C7 의 "회수 뒤에도 남는 것
(1) 워커 슬롯이 반환되지 않는다", `GenerationTimeoutSlotTest` "hang 모드에서는 상한이
지나도 슬롯이 회복되지 않는다"). 그런데 위 16.1분 경로는 **같은 job 의 시도 3번**이고,
시도마다 새 슬롯을 하나씩 먹는다. 앞선 시도의 멈춘 스레드는 슬롯을 돌려주지 않는다.

```
멈춘 시도 누적 = 1, 2, 3
app.worker.concurrency = 3
→ 세 번째 시도가 선점되는 순간 free() = 0
```

`app.worker.concurrency: 3` 인 현재 설정에서는 **hang job 한 건의 세 번째 재시도가
마지막 슬롯을 먹는다.** 그 뒤로는 `workerSlots.free() <= 0` 이라 디스패처가 조회조차 하지
않으므로(인벤토리 3-1 S2), 뒤에 줄 선 job 들은 `HOLDING` 에서 늙기만 하고
**T 에 상한이 없다.** 위 16.1분은 **그 첫 hang job 에 대해서만** 성립한다.

이것은 추측이 아니라 테스트가 이미 적어 둔 사실이다. `HangAbsoluteTimeoutTest` 는
`app.worker.concurrency=4` 로 돌리고 그 이유를 KDoc 에 이렇게 적어 놓았다 —
"멈춘 시도 수가 concurrency 와 같아지면 디스패처가 `free()=0` 을 보고 아무것도 선점하지
못해, job 은 HOLDING 에서 늙고 환불까지 가지 못한다. 즉 **'돈을 푼다'는 멈춘 시도 수 <
concurrency 일 때만 끝까지 간다.** 시도 3번이 전부 멈추는 이 시나리오를 끝까지 보려면
자리가 하나 더 있어야 한다. 이것이 슬롯 누수의 대가다."
(`src/test/kotlin/.../job/concurrency/HangAbsoluteTimeoutTest.kt`)

다만 **그 hang job 자신은 환불까지 간다.** 세 번째 시도가 선점되는 순간의 `free()` 는
아직 1이고(멈춘 시도가 그 시점에는 2개), 최종 환불(`finalRefund`)은 워커 슬롯이 아니라
`DeadJobRecoveryTask` 의 스케줄러 스레드에서 돌기 때문이다(인벤토리 3-1 S6).
`free()` 가 0이 되는 것은 세 번째 시도가 **선점된 뒤**이고, 그때부터 막히는 것은
**그 뒤에 줄 선 다른 job 들**이다. 위 KDoc 의 경고("멈춘 시도 수가 concurrency 와
같아지면")는 그 경계를 일반 규칙으로 적은 것이고, 시도 3번·concurrency 3 이라는
이 조합에서는 마지막 시도까지 선점된다.

슬롯 수 산술은 설정값 산술이며 실측이 아니다. `concurrency: 3` 에서 이 경로를 끝까지
돌려 본 테스트는 없다(`HangAbsoluteTimeoutTest` 는 4로 돈다).

목표 T=10분과 현재 최악을 맞추는 방법(T 를 올릴지, `absolute-timeout-seconds` 를 내릴지,
hang 슬롯 회수를 만들지)은 **Phase 2 항목**이다. 이 요구서는 격차를 기록만 한다.

관련 기존 테스트: `HangAbsoluteTimeoutTest`(멈춘 워커의 돈은 절대 상한이 풀고, 뒤늦게
돌아온 좀비는 아무것도 못 움직인다), `GenerationTimeoutSlotTest`(인벤토리 4-2).
**슬롯 고갈로 T 가 무한해지는 경로를 증명하는 테스트는 없다 — Phase 3 에서 작성.**

### 4-5. INV-06 의 범위 표시

지금 `ledger_entries` 에 UPDATE·DELETE 를 막는 DB 장치가 없다 — 트리거도 권한도
`CHECK` 제약도 V1~V5 어디에도 없다. 앱 코드 쪽도 강제가 아니라 관행이다
(`LedgerRepository` 가 `JpaRepository` 에서 `delete`·`deleteById`·`deleteAll`·`save` merge 를
전부 물려받는다 — 인벤토리 3-4).

**범위 경계 — 2026-09-23 사용자 확정.** `ledger_entries` 는 **삽입만 되는 테이블**로 만든다.
"이 작업에서 기능을 새로 붙이지 않는다"는 원칙과 관련해, 불변식을 강제하는 DB 장치는
기능 추가가 아니라 **불변식 강제 장치**로 보고 Phase 3 허용 범위에 둔다.
마이그레이션을 하나 더 만드는 일이며, 그 마이그레이션이 이 불변식의 구현체다.

강제 수단은 Phase 2 에서 고른다. 후보와 각각이 막는 범위:

| 수단 | 막는 것 | 못 막는 것 |
|---|---|---|
| `BEFORE UPDATE` / `BEFORE DELETE` 트리거에서 `SIGNAL` | 앱·운영자·배치 가릴 것 없이 그 연결이 하는 모든 UPDATE·DELETE | `DROP TRIGGER` 권한을 가진 계정 |
| 앱 DB 계정에서 `UPDATE`·`DELETE` 권한 회수(`REVOKE`) | 앱이 하는 UPDATE·DELETE | 다른 계정(root 등)이 하는 것 |
| 둘 다 | 위 둘의 합 | — |

**주의 — 권한 회수는 테이블 단위로 해야 한다.** 이 앱은 `users`·`jobs` 에 조건부 UPDATE 를
쓰므로(인벤토리 3-1 S1·S3·S5·S6) 스키마 전체에서 UPDATE 를 걷으면 서비스가 죽는다.
`ledger_entries` 한 테이블에만 걸어야 한다.

측정은 순서가 정해져 있다 — **테스트를 먼저 써서 실패시키고**(지금 UPDATE·DELETE 가
그냥 성공한다), 그다음 장치를 붙여 같은 테스트를 통과시킨다. 지시문의
"코드 변경보다 문서와 테스트가 먼저"가 이 순서를 요구한다.

### 4-6. INV-07 — 크래시 지점별 상태

인벤토리 3-2 의 C1~C11 을 그대로 가져와 **자동화 가능/불가능**으로 나눈다.
"부분 통과" 같은 네 번째 상태를 만들지 않고, 행마다 셋 중 하나를 쓴다.

**판정 기준은 INV-07 자신의 목표다** — "재기동 후 INV-02 세 검사 0건이고 묶인 돈이
회수 경로로 풀리는가". 외부 호출이 중복되는지는 INV-04 의 기준이지 INV-07 의 기준이 아니다.
**집계 규칙:** 한 행이라도 실패면 실패, 아니면 하나라도 미측정이면 미측정, 전부 통과면 통과.

| **C11** | SIGTERM 종료 중 드레인 상한 초과 | 가능 | `GenerationDrainOnShutdownTest` "드레인 상한을 넘긴 job 은 포기한 수가 이벤트에 드러나고 PROCESSING 으로 남는다" | **통과** — 인벤토리 4-2 |

[^5]: `HARD_CAP` 이 job 을 PROCESSING 에서 푸는 것 자체는 `HangAbsoluteTimeoutTest` 가 증명한다. 그러나 그 테스트는 `app.worker.concurrency=4` 로 돌고, 운영 설정은 3 이다. 4-4 의 슬롯 산술대로라면 3 에서도 그 job 자신은 환불까지 가지만(세 번째 선점 시점의 `free()` 는 1, 환불은 슬롯을 쓰지 않는다), 그 뒤 슬롯 3개가 영구히 막혀 줄 선 job 들이 선점되지 않는다. 운영 설정에서 그 결말을 재현한 테스트가 없다. 그래서 통과가 아니라 미측정이다. 회수 뒤에도 남는 두 가지(슬롯 미반환, ZSET 고아 멤버 재기록)는 인벤토리 3-2 C7 이 사실로 적고 있다.
[^6]: Redis 장애 중 **회수 경로**는 통과다. 그 상황에서 워커 프로세스까지 죽는 조합은 미측정이다.

**불가능 행의 측정 방법은 여기까지만 쓴다:**
fault injection 플래그로 지정한 지점에서 프로세스를 죽이고,
재기동 후 INV-02 의 세 검사(4-1)를 돌려 0건을 확인한다.
플래그를 어떻게 구현할지(기존 `deploy/observability/faultpad/` 를 확장할지, 별도 프로퍼티를
둘지 — 인벤토리 4-4)는 **Phase 3 의 일**이다.

### 4-7. INV-08 — 외부 완전 장애 10분

외부가 완전히 죽으면 모든 호출이 타임아웃이고, job 은 재시도 3회를 소진한 뒤 전액
환불된다(인벤토리 3-1 S6: `attemptNo + 1 < max-attempts(3)` 이 아니면 `finalRefund`).
4-4 의 산술대로 **한 job 의 직렬 경로는 약 126초**다.

**그러나 N 건을 동시에 넣으면 파이프라인이 상한이다.** 그리고 그 상한은
**"완전 장애"를 스텁으로 어떻게 재현하느냐에 따라 달라진다.** 시도 하나가 잡아먹는
시간이 다르기 때문이다(`job/generation/stub/GenerationStubClient.kt:generate`).

| 재현 방식 | 시도 하나의 소요 | 시도 처리율(슬롯 3개) | 600초에 처리되는 시도 | N 상한 |
|---|---|---|---|---|
| **(A) `app.stub.failure-rate: 1.0`** — 지연은 기본값 3~7초, 그 뒤 예외 | 평균 5초 | 3 ÷ 5 = 0.6 시도/s | 360 | **N ≤ 120** |
| **(B) 타임아웃 유발** — `app.stub.min-delay-millis` 를 `app.generation.timeout-seconds`(20초) 위로 올린다 | 20초(상한까지 기다리고 끊는다) | 3 ÷ 20 = 0.15 시도/s | 90 | **N ≤ 30** |

```
N 건 × 3 시도 = 3N 시도 ≤ 600초 × 시도 처리율
(A) 3N ≤ 360 → N ≤ 120
(B) 3N ≤ 90  → N ≤ 30
```

이 값들은 **상한**이다. job 마다 재시도 사이 backoff 10초·40초가 끼므로 실제 소진은
이보다 느리고, 따라서 실제 N 상한은 위 값 이하다.
부하용 스텁 프로파일(합의 2, 지연을 짧게 낮춘 쪽)로 돌리면 시도 하나가 더 싸져
N 상한이 올라간다 — **부하 프로파일마다 N 을 다시 계산해야 한다.**
어느 재현 방식을 쓸지는 Phase 3 에서 시나리오를 짤 때 정하고, 정한 값을 결과 파일에 적는다.

`N` 이 상한을 넘으면 장애가 끝날 때까지 시도를 다 못 쓴 job 이 남고, 그 job 들은 복구 후
**성공해서 CONFIRM 이 된다.** 그러면 "Σ환불 = Σhold" 는 설계상 거짓이 된다 —
결함이 아니라 목표 서술이 틀린 것이다. 그래서 목표를 두 조각으로 나눈다.

- 기존 단건 증명: `RetryRefundTest`, `GenerationTimeoutRefundTest` (인벤토리 4-2) — **통과**
- 요구서 목표 (i): **N 이 위 표의 상한 이하일 때(재현 방식 (A)면 120, (B)면 30) 동시 투입 + 10분 장애 → 해소 후 Σ환불 = Σhold, 모든 잔액 원상**
- 요구서 목표 (ii): **N 과 무관하게, 장애 중 FAILED 로 종결된 job 에 대해 Σ환불 = Σhold**
  이고 INV-02 세 검사가 0건
- 측정 방법: 장애 해소 후 INV-02 세 검사 0건 + 사용자별 잔액이 투입 전과 같음
- 현재 상태: **미측정**
