# 04. 결과 — 판정과 논증

이 문서는 요구서(`docs/01-requirements.md`)가 세운 PERF 7항목·INV 9항목을 **통과 / 실패 /
미측정** 셋 중 하나로 판정하고, 실패한 것마다 원인·필요한 변경·그 변경이 필요한 Tier 를 적는다.
그다음 Tier A 실측 → Tier B 논증 → Tier C 한계 순으로 결론을 낸다.

## 0. 이 문서의 규율

- **모든 수치에 출처 파일이 붙는다.** 재지 않은 것은 미측정이다.
- **판정은 셋뿐이다.** "부분 통과"·"예상 통과" 같은 네 번째 상태를 만들지 않는다.
  목표가 여러 조건의 AND 인 항목(PERF-03·06·07)은 실측 칸에 어느 조건이 깨졌는지 적고
  판정은 하나로 정한다.
- **실패를 감추지 않는다.** 실패가 하나도 없으면 그것은 시스템이 좋다는 뜻이 아니라
  요구서가 느슨했다는 뜻이다.
- 새 숫자를 만들지 않는다. 아래 숫자는 전부 다음 네 파일에서 온다.

| 약칭 | 파일 |
|---|---|
| **[A]** | `load/results/2026-09-23-tier-a.md` |
| **[S]** | `load/results/2026-09-23-scenarios-02-03-04-and-capacity.md` |
| **[K]** | `load/results/2026-09-23-knob-and-inv03.md` — **가장 최신. [A] 의 인과 하나를 정정한다** |
| **[T]** | `src/test/kotlin/.../invariants/` 의 불변식 테스트 8항목 (커밋 `27aee73`) |

**측정 환경(전 런 공통, [A] "측정 환경").** 호스트 Apple M4 10코어 / 16GiB, Docker VM 8 vCPU /
4GiB, MySQL 8.4 **CPU 4 / 3GiB** (`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`),
앱은 호스트 JVM(힙 2GiB, `ActiveProcessorCount=4`), HikariCP 최대 **10**(기본값, 바꾸지 않음),
k6 도 같은 호스트. **앱·DB·부하 발생기가 한 기계 위에 있다.** 이 사실은 Tier B 논증의
전제이자 한계다(3-2 ⑥).

### 0-1. 먼저 — 앞선 결과 문서의 인과를 정정한다

[A] 와 그 초판 해설은 **"커넥션 대기열 190 → 요청당 19 순번 대기 → p50 5.4초"** 라고 적었다.
**이 인과는 틀렸다.** [K] 2절이 같은 런에서 Hikari 메트릭을 직접 읽어 정정했다.

| 지표 | 값 | 출처 |
|---|---:|---|
| `hikaricp_connections_acquire_seconds_sum ÷ count` | **0.104초** | [K] 2절 |
| `hikaricp_connections_acquire_seconds_max` | 1.626초 | [K] 2절 |
| `hikaricp_connections_timeout_total` | **0** | [K] 2절 |

커넥션 획득은 평균 104ms 로, 클라이언트가 본 5.4초의 **2%** 다. 실제 인과는 이것이다.

```
DB 트랜잭션 1건 ≈ 10.4ms  →  커넥션 10개로 초당 약 960 트랜잭션이 천장
        ↓
톰캣 스레드 200개가 그 처리율에 묶인다
        ↓
k6 가 요구한 나머지 요청은 accept 큐에서 대기
        ↓
클라이언트가 보는 p50 5.4초 = 대부분 accept 큐 대기
```

**병목은 DB 처리율이고, 커넥션 풀은 그 처리율을 나르는 통로다.** 대기열 190 은
"톰캣 스레드 200 − Hikari 활성 10"이 맞지만, 그 대기가 곧 5.4초는 아니다.
이 정정이 처방을 바꾼다 — **풀만 10 → 30 으로 늘려도 DB 가 초당 960 트랜잭션에 머물면
지연은 그대로다.** 이 문서는 전부 정정된 인과로 쓴다.

**다만 이 인과 자체도 계측 + 산술의 추론이지 통제 실험으로 분리된 것이 아니다.**
"풀만 늘린다 / DB 코어만 늘린다"를 따로 돌려 보는 실험은 하지 않았다(3-2 ⑦ 의 2번).

### 하나로 정한 판정의 근거 (AND 목표 항목)

- **PERF-03 → 실패.** 목표 문면이 "PERF-01 의 p50·p99 를 그대로 유지 / 차이가 없어야 통과"다
  (요구서 3절). p50 은 +8% 로 사실상 같지만 p99 가 +70% 다. **두 지표 중 하나라도 어긋나면
  "차이가 없다"가 아니므로 실패로 정했다.** 다만 이 실패는 설계 결함의 증거가 아니라
  **실패 경로의 뒷정리가 접수와 자원을 공유한다**는 증거다(2-3).
- **PERF-06 → 실패.** 목표는 "불변식 위반 0 **그리고** 5분 내 정상 복귀"의 AND 다. 앞은
  완전히 충족했고(오류 0건·불변식 0) 뒤가 깨졌다(복귀 p99 239.68ms > 100ms).
  **AND 이므로 실패다.**
- **PERF-07 → 실패.** 목표는 (i)·(ii)·(iii) 세 조건이고, (iii) 은 요구서 3절에
  **"적체·소진이 게이지로 관측된다"** 로 적혀 있다. (i)·(ii) 는 통과했으나 (iii) 이 깨졌다 —
  게이지가 7.4배 과소 보고했고, 이 문서가 인용하는 적체 수치는 전부 **게이지가 아니라 DB 에서
  직접 센 값**이다([A] 함정 3). 관측이 목표의 일부로 적혀 있는 이상 이것은 실패다.
  ([A] 는 이 항목을 "통과(적체 자체는 목표 밖)"로 적었다 — 이 문서가 (iii) 을 근거로 뒤집는다.
  6절 참조.)

## 2. 실패 항목별 — 원인 · 필요한 변경 · Tier

**`Tier` 칸의 뜻.** "그 변경이 **어느 Tier 의 목표를 맞추기 위해** 필요한가"다.
설계 gap 표(`docs/02-design.md` 2절)의 `닫는 Tier` 와 같은 읽기다 — 변경의 수단이
1대 구성 안에 있느냐가 아니라, **그 목표가 어느 Tier 의 것이냐**로 정한다.

### 2-1. PERF-01 접수 지연 (500 RPS, p50 268배 / p99 117배 초과)

| | |
|---|---|
| **원인** | **DB 처리율이 천장이다.** DB 트랜잭션 1건 ≈ 10.4ms, 커넥션 10개 → 초당 약 960 트랜잭션. 톰캣 스레드 200개가 이 처리율에 묶이고, 넘치는 요청은 accept 큐에서 기다린다([K] 2절). 커넥션 획득 자체는 평균 104ms·타임아웃 0 이므로 **풀 고갈이 원인이 아니다.** 앱 CPU 는 남아 있었다(31~120%, 상한 400% — [A]). |
| **필요한 변경** | **커넥션 풀 확대는 답이 아니다.** [K] 1절이 반대 방향의 증거다 — 워커 동시성을 3 → 50 으로 올려 DB 접근을 늘렸더니 접수가 **257 → 203 RPS 로 21% 느려졌고** p50 은 5,368 → 7,471ms 로 39% 나빠졌다. 같은 DB 처리율을 더 많은 소비자가 나눠 쓴 결과다. 먼저 움직여야 하는 것은 **DB 처리율** 이다 — (a) DB 코어(측정 환경은 4코어이고 부하 중 407%로 상한에 닿았다), (b) 요청당 트랜잭션·커밋 수(접수 1건 = 인증 + TX-1 = 커밋 2회, `sync_binlog=1`·`innodb_flush_log_at_trx_commit=1` 이라 커밋마다 fsync), (c) 앱·DB 의 기계 분리(지금은 같은 기계에서 CPU 를 다툰다). |
| **Tier** | **Tier A.** 500 RPS 는 Tier A 자신의 목표치다(요구서 2-1). 이 변경은 규모가 커져서 필요해지는 것이 아니라 **지금 목표를 맞추려면 필요한 것**이다. 다만 수단(코어 증설·기계 분리)이 1대 구성을 벗어난다는 사실은 3-2 ⑥ 에 적는다. |

### 2-2. PERF-02 조회 지연 (p99 391배 초과)

| | |
|---|---|
| **원인** | **PERF-01 과 같은 원인이고, 같은 줄에 서 있기 때문이다.** 조회도 인증 트랜잭션을 거치고(요구서 합의 6·1-4) 접수와 **같은 커넥션 풀 10개·같은 톰캣 스레드 200개**를 쓴다. 500 RPS 런에서 조회 p99 11,718ms 는 접수 p99 11,728ms 와 사실상 같다 — 조회 쿼리가 느린 것이 아니라 **대기열이 같다.** 150 RPS 구간에서는 10.29ms 로 목표(30ms) 안이다([S] 1절). |
| **필요한 변경** | 2-1 과 같은 DB 처리율 확대. 더해서 **읽기 경로의 분리** — 읽기 전용 커넥션 풀 또는 리플리카. 조회는 쓰기의 3배 부하이므로(요구서 1-1) 같은 풀을 공유하는 한 쓰기 천장이 곧 읽기 천장이다. |
| **Tier** | **Tier A** (2-1 과 같은 이유 — p99 < 30ms 는 Tier A 목표다). 읽기 리플리카는 **Tier B** 에서 비로소 값이 생긴다 — 150 RPS 구간에서는 리플리카 없이도 10.29ms 다. |

### 2-3. PERF-03 외부 지연 무관성 (p50 +8%, p99 +70%)

| | |
|---|---|
| **원인** | **외부 호출은 분리돼 있다. 그 실패의 뒷정리가 분리돼 있지 않다.** p50 이 +8% 에 그친 것이 설계가 맞다는 증거다 — `GenerationClient.generate` 는 다섯 트랜잭션 경계 어디에도 없고 워커 스레드에서 트랜잭션 밖으로 나간다(요구서 3-1). 외부가 60배 느려져도 접수 중앙값은 따라가지 않았다. p99 를 밀어 올린 것은 **실패율 0.3 이 만드는 추가 DB 작업**이다 — `markFailed` → `retry` → `finalRefund` 트랜잭션이 접수와 같은 커넥션 풀 10개를 쓴다([S] 3절). |
| **필요한 변경** | **워커·회수 경로에 별도 커넥션 풀.** 외부 호출 자체는 이미 트랜잭션 밖이므로 남은 것은 뒷정리 트랜잭션의 자원 격리다. 이 변경은 PERF-07·5-1 의 풀 분리와 **같은 하나의 변경**이다. |
| **Tier** | **Tier A.** 풀을 용도별로 나누는 것은 설정·빈 구성 변경이고 1대 구성 안에서 가능하다. 다만 효과는 **미측정**이다([K] 4절이 "관측 풀 분리"를 미측정으로 남겼다). |

### 2-4. PERF-04 대용량 원장 조회 — **미측정으로 남은 이유**

| | |
|---|---|
| **원인(미측정의)** | 1억 행 시드를 돌리지 않았다. 시드 스크립트는 3-A 에서 만들었고(`load/seed/`, 원장 시드는 잔액을 깎는 대신 `initial_balance` 를 올려 INV-01·INV-02 를 함께 지킨다 — 커밋 `4f55511`), 1,000쌍으로 동작만 확인했다. 실제 1억 행 적재와 `EXPLAIN` 은 실행하지 않았다. |
| **필요한 변경** | 먼저 **측정**이다. 요구서 3절·6절 정정 13 이 못 박았듯 **`EXPLAIN` 실행 계획을 보기 전에는 인덱스가 부족한지 판정할 수 없다** — InnoDB 세컨더리 인덱스는 PK 를 접미로 갖기 때문에 `idx_ledger_user_id (user_id)` 단일 컬럼이 `WHERE user_id=? AND id<? ORDER BY id DESC` 를 이미 덮을 가능성이 있다. 계획을 본 뒤에야 `(user_id, id)` 복합 인덱스(`jobs` 에는 V4 로 이미 있다)나 파티셔닝을 말할 수 있다. |
| **Tier** | **측정은 Tier A**(1대에서 가능하다). 계획이 나쁘게 나올 경우의 처방(복합 인덱스)은 Tier A, 파티셔닝·아카이빙은 **Tier C**(요구서 2-3 C-1, 설계 1-5). |

### 2-5. PERF-06 생존 — 복귀 p99 미달, 그리고 **요구서의 전제가 틀렸다**

| | |
|---|---|
| **원인** | 복귀 판정 구간(12~13분)에서 p50 은 6.39ms 로 회복했는데 p99 가 239.68ms 로 남았다. **이 잔여 꼬리의 원인은 미측정이다** — 적체 32만 건이 남긴 테이블 크기, 워커·회수 트랜잭션의 지속, JIT·버퍼풀 상태 중 무엇인지 가르는 측정을 하지 않았다. 계단 측정([S] 1절)에서 워커가 똑같이 포화한 50 RPS 구간의 p99 가 9.74ms 였으므로 "워커가 갉기 때문"이라고 단정할 수 없다. **더 중요한 것은 요구서가 예상한 실패 경로가 오지 않았다는 것이다** — 요구서 PERF-06 은 "예상 경로는 커넥션 고갈"이라 적었고 "오류율 상승은 허용"했는데, 실제로는 3,000 RPS 를 요구해도 **5xx 0건·전송 오류 0건·커넥션 획득 타임아웃 0건**이었다([S] 4절). 시스템은 거절하지 않고 전부 200 으로 받은 뒤 5~11초 기다리게 했다. |
| **필요한 변경** | **백프레셔.** 지금은 서버 지표로 "성공률 100%"인데 사용자는 6초를 기다린다 — 성공률이 건강 지표로서 쓸모를 잃는다. 필요한 것은 (a) 접수 큐·동시 처리 수의 상한과 그것을 넘으면 429/503 으로 **빨리 거절**하기, (b) 거절을 전제로 한 클라이언트 재시도. (b) 가 안전하다는 것은 **측정됐다** — [K] 3절에서 커넥션 타임아웃을 250ms 로 낮춰 일부러 실패시켰을 때 5xx 41,795건·같은 키 재시도 10,767건이 발생했고 **중복 차감은 0** 이었다. 거절해도 돈은 어긋나지 않는다. |
| **Tier** | **Tier A.** 상한과 거절은 1대 구성 안에서 넣을 수 있다. 다만 복귀 p99 를 100ms 안으로 넣는 일은 백프레셔만으로 되는지 알 수 없다 — 위 원인이 미측정이기 때문이다. |

### 2-6. PERF-07 적체 관리 — **관측이 먼저 죽는다**

| | |
|---|---|
| **원인** | 게이지 `credit_hold_outstanding_count` 는 18,890 을 보고했는데 같은 시각 DB 의 HOLDING 은 **140,424** 였다(7.4배). `credit_snapshot_staleness_seconds` 는 **407초** 였고 스냅샷 1주기가 평균 6.4초 걸려 15초 주기를 지키지 못했다([A]). 원인은 구조다 — `DomainSnapshotTask` 가 접수 요청과 **같은 Hikari 풀 10개**를 쓴다. 접수가 풀을 점유하면 스케줄러가 커넥션을 늦게 잡는다. 같은 이유로 워커도 굶는다(부하 10분 동안 COMPLETED 2,120건). |
| **필요한 변경** | 두 가지가 순서대로 필요하고, **순서를 뒤집으면 손해만 본다**([K] 1절이 실측했다). **① 커넥션 풀을 용도별로 분리하고 DB 용량을 먼저 본다. ② 그 다음에 워커 노브.** 노브만 먼저 돌린 실험의 결과: 한가할 때는 25배 이상 올랐지만(150 RPS 투입을 적체 0 으로 따라잡았다), **부하 중에는 슬롯 50개 중 43~49개가 내내 비어 있었고** 실제 처리량은 7.7건/초로 기준선 5.85건/초에서 거의 오르지 않았다. 디스패처도 job 을 선점하려면 커넥션이 필요한데 접수가 풀을 쥐고 있어 슬롯을 채울 수가 없었다. 그러고도 접수는 21% 느려졌다. |
| **Tier** | **풀 분리와 게이지 신선도 경보는 Tier A.** 접수율과 워커 처리량의 **격차 자체를 없애는 장치**(적체 상한, 백프레셔, 워커 스케일아웃)는 설계 gap 표대로 **Tier B** 다. |

### 2-7. INV-05 미결 상한 — 상한이 **없는** 경로

| | |
|---|---|
| **원인** | hang(응답도 타임아웃도 없는 멈춤)은 워커 슬롯을 돌려주지 않는다. 같은 job 의 시도 3번이 슬롯을 하나씩 먹고, `app.worker.concurrency: 3` 에서는 세 번째 시도가 마지막 슬롯을 먹는다. 그 뒤로는 `workerSlots.free() <= 0` 이라 디스패처가 **조회조차 하지 않으므로** 뒤에 줄 선 job 은 `HOLDING` 에서 늙기만 한다. 그 job 들의 T 에는 상한이 없다(요구서 4-4). T 를 10분 → 17분으로 올린 것은 **첫 hang job 의 최악 경로(≈16.1분)** 를 담기 위한 것이고, 이 경로를 닫지 못한다. |
| **필요한 변경** | 멈춘 워커 스레드의 회수 — `TaskExecutor.execute` → `submit` + `(jobId, attemptNo) → Future` 레지스트리, 절대 상한에서 `Future.cancel(true)`. **구조 변경이고, 실제 HTTP 클라이언트가 인터럽트에 반응하는지는 모른다**(설계 gap 표 INV-05 행). 인터럽트가 성공하면 C7 의 잔여 두 가지(슬롯 미반환, ZSET 고아 멤버)가 함께 닫힌다 — `runGeneration` 이 `finally` 에서 `stopHeartbeat` 를 부르기 때문이다(설계 부록 8). |
| **Tier** | **Tier A.** 1대 구성의 결함이고 1대에서 닫아야 한다. 규모와 무관하다. 지금은 `HangSlotStarvationTest` 가 **깨진 상태를 그대로 단언해** gap 을 고정해 두었다 — 고치는 날 그 테스트가 깨지고, 깨지는 것이 gap 을 닫았다는 증거다. |

## 3. 결론 — Tier A → Tier B → Tier C

### 3-1. Tier A 실측 — 이 구성의 상한은 **150 RPS** 다

접수율만 바꿔 3분씩 돌린 계단이다([S] 1절).

| 접수율 | 접수 p50 | 접수 p99 | 조회 p99 | `dropped_iterations` | 판정 |
|---:|---:|---:|---:|---:|---|
| 50 RPS | 4.75ms | 9.74ms | 4.67ms | **0** | 통과 |
| 100 RPS | 3.03ms | 9.69ms | 5.12ms | **0** | 통과 |
| **150 RPS** | **3.35ms** | **19.08ms** | 10.29ms | **0** | **통과 — 여기가 상한** |
| 200 RPS | 3.45ms | 875.56ms | 833.82ms | 591 | 실패 (p99 8.8배 초과) |
| 250 RPS | 373.07ms | 10,487ms | 10,452ms | 17,934 | 붕괴 |
| 500 RPS | 5,368ms | 11,728ms | 11,718ms | 582,327 | 붕괴 |

**`dropped_iterations` 가 0 인 구간만이 유효한 측정이다.** 이 칸이 0 이 아니면 k6 의 도착률
실행기가 새 반복을 띄우지 못하고 버렸다는 뜻이고, 그때의 "접수율"은 **요구한 값이 아니라
시스템이 낸 값**이다. 예: 500 RPS 런의 실제 접수는 257 RPS 이고, 3,000 RPS 스파이크의 실제는
415 RPS 다([S] 4절). 따라서 200 RPS 이상 행의 지연 값은 "그 부하에서의 지연"이 아니라
"그 부하를 요구했을 때 시스템이 낸 지연"으로 읽어야 한다.
**50·100·150 만이 요구한 부하를 그대로 받은 측정이다.**

**무릎의 모양 — 꼬리가 먼저 무너진다.** 150 → 200 에서 p50 은 3.35 → 3.45ms 로 거의 그대로인데
p99 가 19 → 876ms 로 46배 튄다. 200 → 250 에서 비로소 p50 도 무너진다(373ms).
포화는 **꼬리 → 중앙값 → 붕괴** 순서로 온다. p50 이나 평균을 경보 지표로 쓰면
이미 꼬리가 무너진 뒤에 알게 된다.

**실질 용량은 접수가 아니라 워커가 정한다.**

| | 값 | 근거 |
|---|---|---|
| 접수 상한 | 150 RPS | 위 계단 |
| 접수 기준 DAU | 약 162,000 | 150 ÷ 8(피크 배수) × 86,400 ÷ 10(1인 일 쓰기) |
| **처리 기준 DAU** | **약 51,800** | 5.85건/초 × 86,400 ÷ 10 |

둘 중 작은 쪽이 실질 용량이므로 **DAU 약 5만 2천**이고, 요구서가 가정한 DAU 100만의 **1/19** 다.
구속하는 것은 접수가 아니라 워커 처리량이다.

**그 워커 천장은 설정에서 계산된 값과 일치했다.** ADR-004 가 Java 저장소 실측으로 세운 식
`처리량 상한 = min(concurrency / job소요시간, concurrency / 폴링주기)` 에 이 런의 값을 넣으면
`min(3/0.05~0.1, 3/0.5) = 6.0건/초` 이고, 실측은 **5.85건/초** 였다. 구속하는 항은
job 소요시간이 아니라 **폴링 주기**다 — 스텁을 20~140배 빠르게 해도 6건/초에서 막힌다.
이것은 ADR-002(Kafka 제거)가 산술로만 말했던 결론 "전송 수단을 바꿔도 구속하는 항은 움직이지
않는다"의 실측 근거이기도 하다.

**그리고 이 모든 부하 아래에서 원장은 한 건도 어긋나지 않았다.** 사후 정합성 검사를 실제로
돌린 런의 접수 성공 합계는 **625,173건**(01·03·04 와 INV-03 런)이고, 그 뒤 대사 불일치 0 ·
HOLD 누락 0 · 미정산 종결 0 · 음수 잔액 0 이다([S] 5절). 02 핫 계정 런의 114,280건은
`postLoadCheck` 를 돌리지 않아 이 합계에서 뺐다 — 접수 총계로는 739,453건이다.
INV-03 검증 런에서는 5xx 4.2만 건과 재시도 1.1만 건 아래에서도 중복 차감 0 이었다([K] 3절).
**이 시스템은 느려지지만 틀리지 않는다.**

### 3-2. Tier B 논증 — DAU 100만에 무엇이 필요한가

요구서 2-2 는 "무엇을 측정해야 외삽이 가능한가"만 적고 목표 수치를 세우지 않았다.
그 측정이 이제 있으므로 여기서 논증한다. **결론부터: 이 절은 "이만큼 필요하다"까지만 말하고
"그러면 된다"는 말하지 않는다.** 그것은 측정 전에 말할 수 없다.

**목표 수치의 출처.** 요구서 1-1 의 가정(DAU 100만 × 1인 일 쓰기 10회 ÷ 86,400 × 피크 배수 8)
으로 **설계 목표 피크 쓰기 ≈ 926 RPS**(반올림 1,000 RPS), 같은 배수로 **조회 피크 ≈ 2,778 RPS**
다. 실측 상한 150 RPS 는 **조회 450 RPS 를 같은 풀 위에 얹은 상태**에서의 값이므로,
쓰기와 읽기가 같은 비율(1:3)로 함께 커진다는 전제에서 배수를 계산한다.

```
926 ÷ 150 = 6.2배        (반올림 1,000 RPS 기준이면 6.7배)
```

**① 포화 순서는 측정됐다.**

```
DB 처리율  →  톰캣 스레드 200  →  accept 큐  →  클라이언트 지연
                                                  (앱 CPU 는 남았다)
```

부하 중 MySQL CPU 는 상한 400% 에 닿았고(407~410%) 앱 CPU 는 31~120% 로 남았다([A]).
Hikari 획득 타임아웃은 전 런 0 이었다. **먼저 포화하는 것은 DB 이고, 앱이 아니다.**

**② 요구서 2-1 의 커넥션 예산 산술은 맞았다. 빠진 것은 조회다.**
2-1 은 "500 ÷ 10 = 50건/s/커넥션 → 요청당 20ms" 를 예산으로 잡았다. **그 분모에 조회가 없다.**
조회 1건도 인증 트랜잭션을 지나므로(요구서 합의 6) 같은 풀을 쓰고, 부하 모델은 쓰기의 3배다.
같은 10개 커넥션에 실제로 걸린 수요는 500 이 아니라 **2,000 RPS**(접수 500 + 조회 1,500)였고,
그 아래 달성된 것은 접수 257 + 조회 772 = **약 1,029 RPS** 로 [K] 가 계산한 천장(초당 약 960)에
붙어 있다. **예산 산술의 식이 틀린 것이 아니라 분모가 빠져 있었다.**

(주의 — [K] 2절의 "10.4ms × 커넥션 10 = 초당 약 960" 은 곧이어 "초당 약 960 **요청**" 으로 읽힌다.
즉 그 10.4ms 는 요청당 커넥션 점유로 보아야 달성치 1,029 RPS 와 맞는다. 트랜잭션당 10.4ms 로
읽으면 요청당 20.8ms 가 되어 1,029 RPS 를 10개 커넥션으로 낼 수 없다.
**이 문서는 그 값을 요청당으로 읽고, 트랜잭션 단위의 절대값은 주장하지 않는다.**)

**③ 커밋마다 fsync 가 하드 바닥이다.**
`innodb_flush_log_at_trx_commit=1`·`sync_binlog=1` 이므로 접수 1건당 커밋 2회 = fsync 2회다.
926 RPS 면 **초당 약 1,850회의 fsync** 이고, 조회 쪽 인증 트랜잭션까지 세면 더 많다.
이 바닥은 코어를 늘려도 내려가지 않는다 — 내구성 설정을 완화하거나(돈을 다루는 시스템에서
그 자체가 별도의 결정이다), 커밋 수를 줄이거나, 쓰기를 여러 DB 로 나눠야 한다.

**④ 워커 쪽은 접수와 다른, 더 가파른 제약이다.**
실측 5.85건/초에서 목표 926건/초(접수와 균형을 맞추려면)까지는 **약 158배**다.
그리고 **노브만으로는 안 된다는 것이 실측됐다** — 폴링 500 → 50ms, 동시 3 → 50 으로
이론 상한을 667건/초로 올려 놓아도, 부하 중에는 슬롯 43~49개가 놀고 실제는 7.7건/초였다([K] 1절).
디스패처가 커넥션을 못 잡기 때문이다. **순서가 정해졌다: ① 커넥션 풀·DB 용량 → ② 워커 노브.**
반대로 하면 접수까지 21% 느려진다.

**⑤ 그러므로 DAU 100만에 필요한 것은 최소 이만큼이다.**

| # | 필요한 것 | 필요량 | 근거 |
|---|---|---|---|
| 1 | DB 쓰기 처리율 | 현재의 **약 6.2배** (접수 150 → 926 RPS, 조회도 같은 배수). 절대 트랜잭션 수는 위 주의 때문에 적지 않는다 | [S] 1절 계단 + 요구서 1-1 |
| 2 | fsync 처리 능력 | 초당 약 1,850회(접수분만) | [A] 환경, 요구서 1-4 |
| 3 | 워커 처리량 | 현재의 **약 158배** (5.85 → 926건/초) | [A], 요구서 1-1 |
| 4 | 자원 격리 | 접수 / 워커·회수 / 관측이 커넥션 풀을 공유하지 않을 것 | [A] 관측 7.4배 오차, [K] 1-B 슬롯 43~49 유휴 |
| 5 | 백프레셔 | 상한을 넘으면 거절. 거절해도 불변식은 지켜진다는 것은 측정됐다 | [S] 4절, [K] 3절 |

**⑥ 정직하게 — 이 숫자들이 무엇이 아닌지.**
이 측정은 **앱·DB·부하 발생기가 모두 한 기계 위에 있는 구성**의 값이다. DB 컨테이너는
4코어 / 3GiB 이고, 앱 JVM 과 CPU 를 다툰다(요구서 합의 4 가 이미 그렇게 읽으라고 적었다).
k6 도 같은 호스트에서 돈다. **셋을 분리하면 숫자는 달라진다 — 어느 방향으로 얼마나 달라지는지는
모른다.** 위 6.2배는 "이 구성의 150 RPS 에서 926 RPS 까지의 거리"이지 "6.2배의 하드웨어를
주면 된다"가 아니다. 그 둘은 다른 문장이고, 후자는 측정이 없다.

**⑦ Tier B 를 닫으려면 무엇을 더 재야 하나.**

| # | 측정 | 그것이 답하는 질문 |
|---|---|---|
| 1 | 앱·DB·부하 발생기를 **다른 기계로 분리**하고 같은 계단을 다시 | 150 RPS 중 얼마가 이 시스템의 한계이고 얼마가 한 기계를 나눠 쓴 대가인가 |
| 2 | **풀만 확대 / DB 코어만 확대**를 따로 돌리는 통제 실험 | 0-1 의 정정된 인과(DB 처리율이 근원, 풀은 통로)가 실험으로 확인되는가 |
| 3 | 접수 / 워커 / 관측 **풀 분리 후** 같은 부하 | 게이지 7.4배 오차와 슬롯 유휴가 실제로 사라지는가 ([K] 4절이 미측정으로 남긴 항목) |
| 4 | 풀 분리 후 **워커 노브 재실험** | 순서 ①→② 를 지키면 노브가 부하 중에도 듣는가 |
| 5 | **PERF-04** — 원장 1억 행 시드 + `EXPLAIN` + 조회 지연 | 조회 천장이 대기열인가 인덱스인가. 파티셔닝 논의 전체가 여기 걸려 있다 |
| 6 | 백프레셔 도입 후 꼬리 지연과 거절률 | 성공률이 다시 건강 지표가 되는가 |
| 7 | 앱 N대에서 스케줄러 5종의 중복 실행 비용 | 특히 `LedgerReconciliationTask` 가 N배 도는 비용(설계 3-2 후보 1) |

**이 일곱이 비어 있는 한 Tier B 는 "필요량"까지만 말할 수 있다.**

### 3-3. Tier C 한계 — 측정이 뒷받침하는 것과 여전히 추정인 것

요구서 2-3 의 후보 C-1~C-7 을 실측 관점에서 다시 본다. **새 주장을 만들지 않는다.**

| # | 요구서 2-3 의 사실 | 측정 이후 |
|---|---|---|
| **C-1** | 연 73억 행 원장, 파티셔닝·아카이빙 없음 | **여전히 추정.** 최대로 본 것이 원장 215만 행이다([A]). 73억 행에서 무슨 일이 일어나는지는 재지 않았다 |
| **C-2** | `idx_ledger_user_id` 단일 컬럼 | **여전히 추정이고, 판정 불가라는 것이 확인된 사실이다.** PERF-04 가 미측정이므로 `EXPLAIN` 계획이 없다. 인덱스가 부족한지 아닌지 **지금도 말할 수 없다** |
| **C-3** | 대사 배치가 `LEFT JOIN SUM` 으로 전체를 훑는다. 73억 행이면 대사 자체가 부하다 | **부분적으로 측정됐다.** 원장 215만 행·`checkedCount=8` 에서 세 검사가 1.99초였다([A] `postLoadCheck`). 이 한 점은 "가볍다"도 "무겁다"도 증명하지 않는다 — 규모 곡선을 재지 않았다. 73억 행 부분은 추정 |
| **C-4** | 멱등키 7일 보존 → 7천만 행 상주 | **여전히 추정.** 최대 `idempotency_keys` 15,456행을 봤을 뿐이다([K] 3절) |
| **C-5** | 앱 1대·DB 1대 전제, 분산 락 없음 | **여전히 추정이며, 측정할 수 없는 것으로 남았다.** 다중 인스턴스 실측은 요구서 5절 비목표이고 로드맵 결정 13("서버는 1대")이 살아 있다. Tier B 의 N대 논의는 **논증**이지 실측이 아니다(설계 3-2) |
| **C-6** | 워커 처리량 상한 초당 0.43~1.0건 | **측정이 뒷받침한다. 다만 값이 다르다.** 요구서의 0.43~1.0건/s 는 스텁 지연 3~7초 전제의 산술이었고, 부하 프로파일(b, 지연 50~100ms)에서의 실측은 **5.85건/초**다. 값은 달라도 결론은 강화됐다 — 구속하는 항이 job 소요시간이 아니라 **폴링 주기**라는 것이 ADR-004 의 식으로 재현됐고(예측 6.0 vs 실측 5.85), 그래서 스텁을 20~140배 빠르게 해도 천장이 움직이지 않는다 |
| **C-7** | `jobs.next_attempt_at` 에 인덱스 없음 | **여전히 추정.** jobs 테이블이 작은 상태에서만 돌았다. 디스패처 조회가 느려지는 것을 관측한 적이 없다 |

**측정이 새로 더한 한계가 하나 있다.** 요구서 2-3 에 없던 것이다.

> **관측 장치와 자기 회복 장치가 같은 커넥션 풀 위에 서 있다.**
> 부하가 오면 시스템은 뒤처지기만 하는 것이 아니라 **워커(회복)와 스냅샷(관측)을 함께 굶긴다.**
> 계기판이 거짓말을 시작하는 지점이 정확히 대응이 필요한 지점이다([A]).
> 이것은 규모의 한계가 아니라 구조의 한계이므로 Tier C 가 아니라 **지금** 닫을 수 있다.

## 4. 처음부터 다시 한다면 바꿀 결정 3가지

### 결정 1 — 커넥션 풀을 **용도별로 나눈다**

| | |
|---|---|
| **무엇을 다르게** | 접수(요청 처리) / 워커·회수 / 관측·대사가 각각 자기 커넥션 풀을 갖는다. 지금은 셋이 Hikari 기본값 10개 하나를 공유한다. |
| **왜 (측정된 근거)** | 하나의 결정이 **두 사고의 공통 원인**이었다. (i) 관측: 게이지 `credit_hold_outstanding_count` 가 18,890 을 보고할 때 DB 의 실제 HOLDING 은 140,424 였다 — **7.4배 과소 보고**, staleness 407초, 스냅샷 1주기 6.4초([A]). (ii) 워커: 슬롯을 50개로 늘려도 부하 중 **43~49개가 내내 비어 있었고** 처리량은 5.85 → 7.7건/초에 그쳤다. 디스패처가 커넥션을 못 잡아서다([K] 1-B). 그리고 (iii) PERF-03 의 p99 +70% 도 같은 원인이다 — 외부 실패의 뒷정리 트랜잭션이 접수와 같은 풀을 쓴다([S] 3절). |
| **그랬다면 무엇이 달랐을까** | **여기서 말할 수 있는 것은 원인이 특정됐다는 것까지다.** 풀 분리의 효과는 **미측정**이다 — [K] 4절이 "관측 풀 분리"를 미측정 항목으로 남겼다. 측정된 것은 증상(7.4배 오차, 슬롯 43~49 유휴, 접수 −21%)과 그 증상이 공유 풀에서 나온다는 것이지, 분리하면 증상이 사라진다는 것이 아니다. 다만 순서 하나는 실측으로 정해졌다 — **풀이 먼저고 워커 노브가 나중이다.** 반대로 하면 접수가 21% 느려지는 것만 확인했다. |

### 결정 2 — **백프레셔를 처음부터 둔다**

| | |
|---|---|
| **무엇을 다르게** | 접수에 동시 처리 수·대기 시간 상한을 두고, 넘으면 **빨리 거절**한다(429/503). 지금은 상한이 없다. |
| **왜 (측정된 근거)** | 3,000 RPS 스파이크에서 **5xx 0건·전송 오류 0건·커넥션 획득 타임아웃 0건**이었다. 접수 32만 건을 전부 200 으로 받았다. 그런데 사용자는 p50 6,073ms·p99 10,747ms 를 기다렸다([S] 4절). **서버 지표로는 성공률 100% 인데 모바일 클라이언트 기본 타임아웃이면 이미 끊겼을 시간이다.** 요구서 PERF-06 이 "오류율 상승은 허용"이라고 쓴 전제 자체가 틀렸다 — 시스템은 오류를 내지 않고 줄을 세웠고, 그래서 **성공률이 건강 지표로서 쓸모를 잃었다.** |
| **그랬다면 무엇이 달랐을까** | **거절해도 돈은 어긋나지 않는다는 것이 측정됐다.** [K] 3절에서 커넥션 타임아웃을 250ms 로 낮춰 일부러 실패하게 만들었을 때 5xx 41,795건이 나고 클라이언트가 같은 idemKey 로 10,767번 재시도했는데, `jobs` · `idempotency_keys` · `HOLD` 원장이 모두 정확히 15,456 으로 일치했고 중복 차감은 0 이었다. **빨리 실패하고 클라이언트가 재시도하는 모양은 이 시스템의 불변식을 깨지 않는다.** 그것이 측정된 사실이고, 거절률·꼬리 지연이 실제로 어떻게 될지는 재지 않았다. |

### 결정 3 — **처리량 상한을 설정이 아니라 측정으로 정한다**

| | |
|---|---|
| **무엇을 다르게** | `batch-size`·`concurrency`·폴링 주기를 "그럴듯한 값"으로 고르지 않는다. 고르기 전에 그 셋이 만드는 처리량 상한 식을 쓰고, 목표 처리량을 대입해 값을 역산한 뒤, 그 값으로 실제로 잰다. |
| **왜 (측정된 근거)** | batch-size 20 은 근거 없이 정해졌고 나중에 3 으로 내려왔다(ADR-004). 폴링 500ms 도 마찬가지다. 그 결과 처리량 상한이 `min(3/0.05~0.1, 3/0.5) = 6.0건/초` 로 **폴링 주기에 묶였고**, 한 달 뒤 Kotlin 이식판에서 **5.85건/초**로 같은 천장이 다시 나왔다(ADR-004 는 2026-08-20, 이 측정은 2026-09-23 — [A]). 값 하나가 잘못된 것이 아니라 **구속하는 항이 무엇인지 아무도 몰랐던 것**이 문제다 — job 을 20~140배 빠르게 해도 천장은 움직이지 않는다. 이 시스템의 실질 DAU 를 5만 2천으로 묶은 것이 접수가 아니라 이 숫자다([S] 1절). |
| **그랬다면 무엇이 달랐을까** | **설정이 한가할 때는 실제로 듣는다는 것이 측정됐다.** 폴링 500 → 50ms, 동시 3 → 50 으로 바꾸자 150 RPS 투입 9,001건에 대해 적체가 **0** 이었다 — 기준선의 25분 소진이 실시간 처리가 됐다([K] 1-A). 즉 값을 처음부터 측정으로 정했다면 **한가한 구간의 천장은 확실히 달랐다.** 부하 구간은 다르다 — 같은 노브로 500 RPS 를 걸면 슬롯이 놀고 접수가 21% 느려졌으므로([K] 1-B·1-C), "측정으로 값을 정했더라면 부하에서도 빨랐을 것"은 **측정이 부정한다.** 측정으로 정하는 일에는 결정 1(풀 분리)이 선행해야 한다는 것까지가 실측이 말해 주는 범위다. |

**셋을 고른 이유.** 세 결정은 각각 이 문서의 실패 항목 여러 개를 동시에 가리킨다 —
결정 1 은 PERF-03·PERF-07(관측)·워커 굶주림을, 결정 2 는 PERF-06 과 "성공률이 거짓말하는"
문제를, 결정 3 은 PERF-07 의 격차와 실질 DAU 상한을 만든다. 후보로 검토한 나머지 둘
(원장 append-only 를 첫 마이그레이션에 넣기, 관측 지표에 신선도 경보를 처음부터 붙이기)은
각각 운영 배포 조건 하나(`log_bin_trust_function_creators`)와 경보 하나의 문제로,
위 셋보다 걸리는 실패 항목이 적어 제외했다.
