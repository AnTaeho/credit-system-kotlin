# 크레딧 시스템

느리고 자주 실패하는 외부 API 앞에 크레딧을 둔다.
선불로 산 크레딧이 요청 한 건마다 차감된다.

> **외부가 죽든, 서버가 죽든, 같은 요청이 열 번 오든 — 돈은 정확히 한 번만 움직여야 한다.**

Kotlin · Spring Boot 4.1 · MySQL 8.4 · Redis 7
이 문서가 정본이다. 코드와 어긋나면 **코드가 맞다.**

## 요약

- **돈은 지켜진다.** 차감 62만 5천 건 뒤 원장 불일치 0. 5xx 4.2만 건·재시도 1.1만 번에도 중복 0
- **용량은 150 RPS.** 그 위에서는 꼬리부터 무너진다(200 RPS 에서 p99 가 19ms → 876ms)
- **실질 상한은 DAU 5.2만.** 접수가 아니라 워커 처리량(6건/초)이 정한다

  다시 열렸다** — 접수를 8개로 묶어 풀 경합을 0으로 만들어도 신선도는 그대로였다(4·5절)

## 1. 무엇을 보증하는가

네 가지를 보증한다. 전부 테스트가 있고, 전부 부하에서 확인했다.

| 불변식 | 확인된 것 |
|---|---|
| 잔액은 음수가 되지 않는다 | 잔액 100·비용 1 에 동시 1,000건 → 정확히 100건 성공 |
| 원장 합계 = 잔액 | 차감 62만 5천 건 뒤 세 검사 전부 0 |
| 같은 멱등키는 한 번만 청구된다 | 5xx 4.2만·재시도 1.1만 → 중복 차감 0 |
| 원장은 삽입만 된다 | UPDATE·DELETE 를 DB 가 거부(`ERROR 1644`) |

### 지키는 장치 — 전부 애플리케이션 밖에 있다

| 장치 | 막는 것 |
|---|---|
| `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?` | 음수 잔액 |
| `UNIQUE (user_id, idem_key)` + 앱 선조회 | 이중 차감 |
| `WHERE status = ? AND attempt_no = ?` (CAS) | 늦게 돌아온 워커의 덮어쓰기 |
| `BEFORE UPDATE/DELETE → SIGNAL` (V6 트리거) | 원장 변조 |

읽고-빼고-쓰기 대신 **조건을 SQL 에 넣는다.** 0행이면 거절이다.
앱이 몇 대든 스레드가 몇 개든 같은 보장이 선다.

## 2. 흐름

```
S1  접수 TX      멱등키 INSERT → 잔액 조건부 차감 → job(HOLDING) → HOLD 원장(−100)
S2  대기         디스패처가 0.5초마다 HOLDING 을 집는다
S3  선점 CAS     HOLDING → PROCESSING (attemptNo 일치할 때만). heartbeat 시작
S4  외부 호출    ★ 어떤 트랜잭션에도 들어 있지 않다
S5  확정 TX      PROCESSING → COMPLETED + CONFIRM 원장(0)
S6  회수         만료·정체·상한 → FAILED → 재시도 또는 REFUND(+100)
```

트랜잭션 경계는 다섯이다(S1 · confirm · markFailed · retry · finalRefund).
**외부 호출은 그중 어디에도 없다.** 안에 두면 커넥션 예산이 이렇게 된다:

```
외부 200ms → 커넥션 10 ÷ 0.2초 = 초당  50건
외부   2초 → 커넥션 10 ÷   2초 = 초당   5건
외부   5초 → 커넥션 10 ÷   5초 = 초당   2건
```

## 3. 회수 정책

`DeadJobRecoveryTask` 가 5초마다 세 단계를 돈다.

| 판정 | 조건 | 걸리는 시간 |
|---|---|---|
| heartbeat 만료 | ZSET score 지남 | 10~15초 |
| 정체 (backstop) | `updatedAt < now − 60초`, heartbeat 없음/불명 | 60~65초 |
| **절대 상한** | heartbeat 가 **살아 있어도** `updatedAt < now − 300초` | 300초 |

세 번째가 핵심이다.
없으면 **hang 인 워커의 종지기가 영원히 갱신해 돈이 영구히 묶인다.**

재시도는 지수 backoff(10초 · 40초), 상한 3회. 소진하면 전액 환불.

| 층 | 값 |

| 커넥션 풀 | HikariCP 기본 10 — **바꾸지 않았다** |
| 부하 발생기 | k6 v1.6.0 |

### 용량 — 계단으로 찾은 무릎

| 접수율 | p50 | p99 | |
|---:|---:|---:|---|
| 100 RPS | 3.03ms | 9.69ms | 통과 |
| **150 RPS** | **3.35ms** | **19.08ms** | **통과 — 상한** |
| 200 RPS | 3.45ms | **875ms** | 실패 |
| 250 RPS | 373ms | 10,487ms | 붕괴 |
| 500 RPS | 5,368ms | 11,728ms | 붕괴 |

**꼬리가 먼저 무너진다.** 150 → 200 에서 p50 은 그대로인데 p99 가 46배 튄다.
그래서 **p50 · 평균 · 성공률은 경보로 쓰지 않는다.**

### 세션 인증으로 다시 재도 무릎은 그대로다

위 계단은 **개발 로그인 헤더**로 쟀다. 그 경로는 요청마다 `findByEmail` 트랜잭션이 하나 더 돈다
— 운영(구글 OIDC + 세션 쿠키)에는 없는 비용이다. "그래서 150 은 과소평가"라고 보고
**세션 인증으로 다시 쟀다**(`load/k6/06-session-auth.js`, 워밍업 45초 제외).

| 접수율 | 헤더 인증 p50 / p99 | **세션 인증 p50 / p99** |
|---:|---:|---:|
| 150 RPS | 3.35 / **19.08ms** | 4.17 / **33.35ms** |
| 175 RPS | — | 3.78 / 416ms |
| 200 RPS | 3.45 / 875ms | 8.64 / **734ms** |
| 250 RPS | 373 / 10,487ms | 123 / 2,837ms |
| 300 RPS | — | 1,916 / 4,889ms |

**예상이 틀렸다.** 요청당 커밋을 2회에서 1회로 줄였는데 **무릎은 여전히 150~200 사이**다.
높은 부하에서 덜 나빠지긴 한다(250 RPS 에서 p50 373 → 123ms). 그러나 상한은 안 올라갔다.

즉 **인증 트랜잭션은 병목이 아니었다.** 접수 트랜잭션(TX-1) 자체와 그 커밋이 비용을 쥐고 있다.

### 175 RPS 에서 드러난 또 하나 — 이 측정 구성의 한계

175 RPS 세션 인증에서 **자원은 전혀 안 찼는데** p99 가 416ms 였다.

| 지표 | 값 |
|---|---|
| MySQL CPU | 23~153% (상한 400%) |
| Hikari active | 1~3 / 10 |
| Hikari pending | **0** |
| G1 Young GC | 24회, 중앙 16ms, **최대 72ms** |

DB 도 풀도 한가한데 꼬리만 길다. 후보는 셋이고 **가르지 못했다** —
GC 일시정지(최대 72ms), VU 가 늘 때마다 도는 로그인(HTML 렌더 2회 포함),
그리고 **k6 가 앱과 같은 10코어를 나눠 쓰는 것**.

> 여기서부터는 앱·DB·부하 발생기를 **다른 기계**로 떼지 않으면 더 정밀해지지 않는다.
> 150 RPS 라는 값은 그 한계 안에서의 값이다.

### 처리량 천장

```
처리량 상한 = min(동시성 ÷ job소요, 동시성 ÷ 폴링주기)
            = min(30~60, 6.0)
            = 6.0 건/초

실측 5.85 건/초   ← 13개월 전 Java 판 벤치마크가 잰 5.8 TPS 와 같은 값
```

외부를 140배 빠르게 해도 **폴링 주기가 막는다.**

| 기준 | 환산 DAU |
|---|---:|
| 접수 (150 RPS) | 16만 |
| **처리 (6건/초)** | **5.2만** ← 실질 용량 |

가정한 DAU 100만의 1/19 다.

### 정합성

| | |
|---|---|
| 차감 | **625,173건** (사후 검사를 실제로 돌린 런 합계) |

### 커넥션을 접수와 배경 작업에 나눠 보면 — 벌크헤드 A/B

**같은 바이너리, 환경변수 하나만 다르다.** 접수 경로(`/api/**`)의 동시 진입을 세마포어로
묶어 풀 10개 중 2개를 배경 작업 몫으로 남긴다. 껐을 때 미터가 아예 없는 것으로 켬/끔을 확인했다.
500 RPS · 3분 · 스케줄러 켬 · 매 런 볼륨 초기화. 각 1회 — **재현 미확인.**

| | A `permits=0` (끔) | B `permits=8` (켬) | |
|---|---:|---:|---|
| 완료된 job | 752 | **1,086** | **+44%** |
| 접수 처리량 | 1,645 req/s | 1,227 req/s | **−25%** |
| 접수 p50 | 1,304ms | 4,718ms | 3.6배 악화 |
| 접수 p99 | 7,022ms | **6,222ms** | 개선 |
| p99 − p50 (꼬리 폭) | 5,718ms | **1,504ms** | 3.8배 축소 |
| Hikari 대기 스레드 | 190 | **0** | — |
| 게이지 신선도 최대 | 16.2초 | 18.5초 | 차이 없음 |

**대기가 사라진 게 아니라 자리를 옮겼다.** 허가 대기 평균은 156ms(`sum/count` = 35,645s /
228,163건)이고, 이것과 처리량 1,227/s 를 곱하면 묶여 있는 요청이 **192개** — 끔에서 Hikari 가
세던 190개와 같은 수다. 5초에 가까운 지연은 여전히 톰캣 accept 큐다(6절 (1)과 같은 그림).

**채택하지 않았다.** 배경 작업은 분명히 살아났지만(+44%), 세마포어가 묶는 것은 커넥션이 아니라
**요청**이다. 요청 한 건은 DB 를 만지는 시간보다 오래 살아 있으므로, 허가 8개는 커넥션 8개어치
일보다 훨씬 적은 일만 시킨다 — 그래서 접수가 25% 느려졌다. 남겨 둔 커넥션 2개도 대부분 놀았다
(배경 작업은 초당 6건 수준이다). **여유분을 남기는 값을 고정하는 방식의 구조적 한계다.**
기본값 0(끔)으로 코드에 남긴다. 켜는 것은 측정에서 환경변수로만 한다.

> **이 런은 결함 (1)을 재현하지 못했다.** 신선도는 양쪽 모두 15초 주기 + 주기 소요(1.8~5초)로
> 설명되는 톱니였고, 게이지와 DB 의 차이도 정확히 한 주기치였다(A 16.4초분, B 18.3초분).
> 3분으로는 407초짜리 고장이 나타나지 않는다. **벌크헤드가 (1)을 고치는지는 측정되지 않았다.**

## 5. 알려진 결함 셋

접수 · 워커 · 회수 · 대사 · 스냅샷이 **Hikari 풀 10개를 공유한다.** (2)는 이것이 원인임이
확인됐고, (3)은 애초에 다른 문제이며, (1)은 **원인이 다시 열렸다** — 아래를 보라.

### (1) 관측이 먼저 죽는다

| | |
|---|---|
| 게이지가 말한 적체 | 18,890 |
| **DB 실제값** (같은 시각) | **140,424** |
| 게이지 신선도 | **407초** (15초 주기여야 한다) |

**대응이 필요한 바로 그 순간에 계기판을 믿을 수 없다.** 증상은 실측이다. 원인은 아니다.

처음엔 "스냅샷 태스크가 커넥션을 못 잡는다"고 적었다. **근거가 없다.** 벌크헤드를 켜서 Hikari
대기 스레드를 190 → 0 으로 만들어도 신선도는 그대로였고(위 A/B), 부하를 완전히 멈춘 상태에서
HOLDING 55,252행을 놓고 재 보니 **주기 한 번이 3.8~5.0초** 걸렸다 — 경합이 0인데도 그렇다.
6절 (1)이 기록한 "Hikari 획득 최대 1.63초"와도 어긋난다. 1.63초 안에 잡히는 커넥션이
407초를 만들 수는 없다.

남은 후보 셋. **어느 것도 아직 측정되지 않았다.**

| 후보 | 왜 그럴듯한가 | 반증/확인 방법 |
|---|---|---|
| 주기 쿼리 자체가 무겁다 | 6개 집계 쿼리, 적체에 비례해 늘어난다. 버퍼 풀 128MiB | `credit_snapshot_duration_seconds_max` |
| 주기가 통째로 실패해 삼켜진다 | 예외가 나면 이벤트를 발행하지 않는다 → 신선도만 오르고 **소요 시간 미터엔 아무것도 안 남는다** | `credit_snapshot_cycles` 가 멈추는지 |
| 스케줄러 풀 4개를 다른 태스크가 점유 | 회수·대사가 같은 풀에 있다 | 태스크별 실행 로그 간격 |

두 번째 후보가 맞다면 "커넥션을 못 잡는다"가 다시 원인이 될 수 있다 — 단 기전은 "느려진다"가
아니라 **"주기가 버려진다"** 다. 둘은 처방이 다르다. 10분 런에서 세 미터를 같이 재야 갈린다(9절).

### (2) 워커가 굶는다

10분 부하에 2,120건만 처리했다.
슬롯을 3 → 50 으로 늘려 봤더니 **43~49개가 내내 비어 있었다** — 디스패처도 선점하려면
커넥션이 필요하기 때문이다. 접수는 오히려 **257 → 203 RPS** 로 느려졌다.

> 워커 노브는 한가할 때만 듣는다. 적체가 쌓이는 상황 — 그 설정이 필요한 바로 그 상황 — 에서는
> 듣지 않는다. **커넥션 풀이 먼저다.**

### (3) 백프레셔가 없다

3,000 RPS 를 요구해도 **5xx 0건 · 성공률 100%** 로 전부 받고 6초 기다리게 한다.
서버 지표는 건강해 보이는데 사용자는 이미 타임아웃이다.
**성공률이 건강 지표로서 쓸모를 잃는다.**

거절이 안전하다는 것은 측정됐다 — 일부러 5xx 를 4.2만 건 냈을 때 중복 차감이 0이었다.

### (덤) hang 이 슬롯을 돌려주지 않는다

절대 상한이 돈은 풀지만 스레드는 영영 묶인다.
슬롯이 다 차면 **뒤에 줄 선 job 은 상한이 없다.**
인터럽트를 보내려면 `Future` 가 필요한데 지금은 `execute` 가 버린다.

## 6. 측정이 바꾼 결론 둘

### (1) 5.4초의 정체는 커넥션 대기가 아니었다

처음엔 "대기열 190개가 5.4초를 만든다"고 적었다. **틀렸다.**

| Hikari 획득 시간 | 값 |
|---|---:|
| 평균 | **104ms** (5.4초의 2%) |
| 최대 | 1.63초 |
| 타임아웃 | 0 |

```
DB 트랜잭션 ≈ 10.4ms × 커넥션 10 = 초당 약 960 요청
→ 톰캣 스레드 200개가 그 처리율에 묶인다
→ 나머지는 accept 큐에서 대기        ← 5.4초의 대부분
```

**병목은 DB 처리율이고 커넥션 풀은 통로다.** 이 정정이 처방을 바꿨다 —
실제로 워커 동시성을 3 → 50 으로 올려 DB 접근을 늘렸더니 접수가 **21% 느려졌다.**

### (2) 원장 1억 행에서 느린 것은 조회가 아니라 대사였다

| 조건 | 조회 p99 |
|---|---:|
| 워밍 · 스케줄러 끔 | **10ms** |
| **워밍 · 스케줄러 켬** (운영 기본값) | **8,489ms** |

대사 쿼리가 **265초 지나도 끝나지 않았다.** 원인은 `LIMIT 100` 이 `GROUP BY` **뒤에** 걸리는 것 —
100명을 얻으려고 1억 행 전부를 집계한다. 커서가 줄이는 것은 출력이지 스캔이 아니다.

**고쳤다.** 사용자 id 100개를 먼저 확정하고(집계 없음 → `LIMIT` 이 스캔을 끊는다)
그 100명의 원장만 집계한다. 테스트 350건 그대로 통과. **개선 폭은 미측정.**

부수 확인: **인덱스는 충분하다.** `idx_ledger_user_id (user_id)` 단일 컬럼으로
`Backward index scan`(filesort 없음) — InnoDB 가 PK 를 접미로 갖기 때문이다.
복합 인덱스도, 이 이유로는 파티셔닝도 필요 없다.
