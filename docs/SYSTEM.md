# 크레딧 시스템

느리고 자주 실패하는 외부 API 앞에 크레딧을 둔다.
선불로 산 크레딧이 요청 한 건마다 차감된다.

> **외부가 죽든, 서버가 죽든, 같은 요청이 열 번 오든 — 돈은 정확히 한 번만 움직여야 한다.**

Kotlin · Spring Boot 4.1 · MySQL 8.4 · Redis 7
이 문서가 정본이다. 코드와 어긋나면 **코드가 맞다.**

---

## 요약

- **돈은 지켜진다.** 차감 62만 5천 건 뒤 원장 불일치 0. 5xx 4.2만 건·재시도 1.1만 번에도 중복 0
- **용량은 150 RPS.** 그 위에서는 꼬리부터 무너진다(200 RPS 에서 p99 가 19ms → 876ms)
- **실질 상한은 DAU 5.2만.** 접수가 아니라 워커 처리량(6건/초)이 정한다
- **부하에서 계기판이 먼저 죽는다.** 적체 게이지가 7.4배 과소 보고, 신선도 407초
- **결함 셋의 원인이 하나다.** 접수·워커·관측이 커넥션 풀 10개를 나눠 쓴다

## 1. 무엇을 보증하는가

네 가지를 보증한다. 전부 테스트가 있고, 전부 부하에서 확인했다.

| 불변식 | 확인된 것 |
|---|---|
| 잔액은 음수가 되지 않는다 | 잔액 100·비용 1 에 동시 1,000건 → 정확히 100건 성공 |
| 원장 합계 = 잔액 | 차감 62만 5천 건 뒤 세 검사 전부 0 |
| 같은 멱등키는 한 번만 청구된다 | 5xx 4.2만·재시도 1.1만 → 중복 차감 0 |
| 원장은 삽입만 된다 | UPDATE·DELETE 를 DB 가 거부(`ERROR 1644`) |

### 지키는 장치 — 전부 애플리케이션 밖에 있다

| 장치 | 막는 것 |
|---|---|
| `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?` | 음수 잔액 |
| `UNIQUE (user_id, idem_key)` + 앱 선조회 | 이중 차감 |
| `WHERE status = ? AND attempt_no = ?` (CAS) | 늦게 돌아온 워커의 덮어쓰기 |
| `BEFORE UPDATE/DELETE → SIGNAL` (V6 트리거) | 원장 변조 |

읽고-빼고-쓰기 대신 **조건을 SQL 에 넣는다.** 0행이면 거절이다.
앱이 몇 대든 스레드가 몇 개든 같은 보장이 선다.

## 2. 흐름

```
S1  접수 TX      멱등키 INSERT → 잔액 조건부 차감 → job(HOLDING) → HOLD 원장(−100)
S2  대기         디스패처가 0.5초마다 HOLDING 을 집는다
S3  선점 CAS     HOLDING → PROCESSING (attemptNo 일치할 때만). heartbeat 시작
S4  외부 호출    ★ 어떤 트랜잭션에도 들어 있지 않다
S5  확정 TX      PROCESSING → COMPLETED + CONFIRM 원장(0)
S6  회수         만료·정체·상한 → FAILED → 재시도 또는 REFUND(+100)
```

트랜잭션 경계는 다섯이다(S1 · confirm · markFailed · retry · finalRefund).
**외부 호출은 그중 어디에도 없다.** 안에 두면 커넥션 예산이 이렇게 된다:

```
외부 200ms → 커넥션 10 ÷ 0.2초 = 초당  50건
외부   2초 → 커넥션 10 ÷   2초 = 초당   5건
외부   5초 → 커넥션 10 ÷   5초 = 초당   2건
```

## 3. 회수 정책

`DeadJobRecoveryTask` 가 5초마다 세 단계를 돈다.

| 판정 | 조건 | 걸리는 시간 |
|---|---|---|
| heartbeat 만료 | ZSET score 지남 | 10~15초 |
| 정체 (backstop) | `updatedAt < now − 60초`, heartbeat 없음/불명 | 60~65초 |
| **절대 상한** | heartbeat 가 **살아 있어도** `updatedAt < now − 300초` | 300초 |

세 번째가 핵심이다.
없으면 **hang 인 워커의 종지기가 영원히 갱신해 돈이 영구히 묶인다.**

재시도는 지수 backoff(10초 · 40초), 상한 3회. 소진하면 전액 환불.

## 5. 알려진 결함 셋

**셋의 원인이 하나다** — 접수 · 워커 · 회수 · 대사 · 스냅샷이 **Hikari 풀 10개를 공유한다.**

### (1) 관측이 먼저 죽는다

| | |
|---|---|
| 게이지가 말한 적체 | 18,890 |
| **DB 실제값** (같은 시각) | **140,424** |
| 게이지 신선도 | **407초** (15초 주기여야 한다) |

스냅샷 태스크가 커넥션을 못 잡는다.
**대응이 필요한 바로 그 순간에 계기판을 믿을 수 없다.**

### (2) 워커가 굶는다

10분 부하에 2,120건만 처리했다.
슬롯을 3 → 50 으로 늘려 봤더니 **43~49개가 내내 비어 있었다** — 디스패처도 선점하려면
커넥션이 필요하기 때문이다. 접수는 오히려 **257 → 203 RPS** 로 느려졌다.

> 워커 노브는 한가할 때만 듣는다. 적체가 쌓이는 상황 — 그 설정이 필요한 바로 그 상황 — 에서는
> 듣지 않는다. **커넥션 풀이 먼저다.**

### (3) 백프레셔가 없다

3,000 RPS 를 요구해도 **5xx 0건 · 성공률 100%** 로 전부 받고 6초 기다리게 한다.
서버 지표는 건강해 보이는데 사용자는 이미 타임아웃이다.
**성공률이 건강 지표로서 쓸모를 잃는다.**

거절이 안전하다는 것은 측정됐다 — 일부러 5xx 를 4.2만 건 냈을 때 중복 차감이 0이었다.

### (덤) hang 이 슬롯을 돌려주지 않는다

절대 상한이 돈은 풀지만 스레드는 영영 묶인다.
슬롯이 다 차면 **뒤에 줄 선 job 은 상한이 없다.**
인터럽트를 보내려면 `Future` 가 필요한데 지금은 `execute` 가 버린다.

## 6. 측정이 바꾼 결론 둘

### (1) 5.4초의 정체는 커넥션 대기가 아니었다

처음엔 "대기열 190개가 5.4초를 만든다"고 적었다. **틀렸다.**

| Hikari 획득 시간 | 값 |
|---|---:|
| 평균 | **104ms** (5.4초의 2%) |
| 최대 | 1.63초 |
| 타임아웃 | 0 |

```
DB 트랜잭션 ≈ 10.4ms × 커넥션 10 = 초당 약 960 요청
→ 톰캣 스레드 200개가 그 처리율에 묶인다
→ 나머지는 accept 큐에서 대기        ← 5.4초의 대부분
```

**병목은 DB 처리율이고 커넥션 풀은 통로다.** 이 정정이 처방을 바꿨다 —
실제로 워커 동시성을 3 → 50 으로 올려 DB 접근을 늘렸더니 접수가 **21% 느려졌다.**

### (2) 원장 1억 행에서 느린 것은 조회가 아니라 대사였다

| 조건 | 조회 p99 |
|---|---:|
| 워밍 · 스케줄러 끔 | **10ms** |
| **워밍 · 스케줄러 켬** (운영 기본값) | **8,489ms** |

대사 쿼리가 **265초 지나도 끝나지 않았다.** 원인은 `LIMIT 100` 이 `GROUP BY` **뒤에** 걸리는 것 —
100명을 얻으려고 1억 행 전부를 집계한다. 커서가 줄이는 것은 출력이지 스캔이 아니다.

**고쳤다.** 사용자 id 100개를 먼저 확정하고(집계 없음 → `LIMIT` 이 스캔을 끊는다)
그 100명의 원장만 집계한다. 테스트 350건 그대로 통과. **개선 폭은 미측정.**

부수 확인: **인덱스는 충분하다.** `idx_ledger_user_id (user_id)` 단일 컬럼으로
`Backward index scan`(filesort 없음) — InnoDB 가 PK 를 접미로 갖기 때문이다.
복합 인덱스도, 이 이유로는 파티셔닝도 필요 없다.

## 7. 설계 결정 이력

| 시점 | 결정 | 근거 |
|---|---|---|
| 2026-07 | Kafka + outbox 도입 | 최초 스펙이 규정. **당시 수치 없음** |
| 2026-07 | 낙관적 락 → 조건부 UPDATE | 재시도 루프 제거 |
| 2026-08 | **Kafka 제거, jobs 가 큐** | 이중 쓰기와 outbox 재발행이 사라진다 |
| 2026-08 | `batch-size` 20 → 3 | 30셀 벤치마크. **유일한 측정 기반 결정** |
| 2026-08 | confirm 재시도 제거 | 정합성은 회수가 지킨다. 대가는 외부 호출 중복 |
| 2026-09 | 사용자별 속도 제한 제거 | 총량은 잔액, 동시성은 워커 수가 막는다 |
| 2026-09 | 드레인 복원 | 검증 수단이 생긴 뒤 되살렸다 |
| 2026-09 | 원장 append-only 강제 | 관행을 DB 제약으로 |
| 2026-09 | 대사 배치 두 단계 분리 | 6절 (2) |

**Kafka 재도입 트리거** (전부 가정)

- 폴링을 X ms 로 내려도 선점 지연 p99 가 Y 초과
- 컨슈머 그룹이 둘 이상 필요
- 다중 인스턴스에서 `claim` 실패율이 Z% 초과

## 8. 운영

### 배포를 막는 것

- [ ] **운영 DB 에 `log_bin_trust_function_creators=1`**
      없으면 V6 마이그레이션이 `ERROR 1419` 로 실패해 **배포가 멈춘다** (실행으로 확인함)
- [ ] 예상 피크가 **150 RPS 이하**인가
- [ ] 대사 주기(60초)가 원장 규모에서 한 주기 안에 끝나는가

### 경보

| 지표 | 임계 | 왜 |
|---|---|---|
| `snapshot staleness` | > 45초 | **이게 울리면 다른 게이지는 전부 무효** |
| `hikari pending` | > 20 | 포화의 가장 이른 신호 |
| 접수 p99 | > 100ms | 꼬리가 먼저 무너진다 |

**쓰지 않을 것**: p50 · 평균 · 성공률 (붕괴 직전에도 정상으로 보인다)
