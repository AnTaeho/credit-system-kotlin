# 크레딧 시스템 — 한 장짜리 문서

느리고 자주 실패하는 외부 API 앞에 크레딧을 둔다. 선불로 산 크레딧이 요청 한 건마다 차감된다.
**외부가 죽든 서버가 죽든 같은 요청이 열 번 오든, 돈은 정확히 한 번만 움직여야 한다.**

Kotlin · Spring Boot 4.1 · MySQL 8.4 · Redis 7.
이 문서가 정본이다. 상세 근거는 git 이력(태그 `req-v0`~`req-v3`)과 포트폴리오 아티팩트에 있다.

---

## 1. 흐름 — 요청 하나가 지나는 여섯 단계

```
S1  접수 TX      멱등키 INSERT → 잔액 조건부 차감 → job(HOLDING) → HOLD 원장(−100)   [한 트랜잭션]
S2  대기         디스패처가 0.5초마다 HOLDING 을 집는다 (nextAttemptAt 지난 것만)
S3  선점 CAS     HOLDING → PROCESSING, attemptNo 일치할 때만. Redis heartbeat 시작
S4  외부 호출    ★ 어떤 트랜잭션에도 들어 있지 않다
S5  확정 TX      PROCESSING → COMPLETED + CONFIRM 원장(0)                            [한 트랜잭션]
S6  회수         heartbeat 만료 / 정체 / 절대 상한 → FAILED → 재시도 또는 REFUND(+100)
```

트랜잭션 경계는 다섯이다(S1, confirm, markFailed, retry, finalRefund).
**외부 호출은 그 다섯 중 어디에도 없다.**

## 2. 돈을 지키는 장치 셋 — 전부 애플리케이션 밖에 있다

| 장치 | 무엇을 막나 |
|---|---|
| `UPDATE users SET balance = balance - ? WHERE id = ? AND balance >= ?` | 음수 잔액. 읽지 않고 조건을 SQL 에 넣는다. 0행이면 거절 |
| `UNIQUE (user_id, idem_key)` + 앱 선조회 | 이중 차감. 앱 검사의 경쟁을 DB 제약이 받는다 |
| `WHERE status = ? AND attempt_no = ?` (CAS) | 늦게 돌아온 워커의 덮어쓰기. 회수된 시도는 0행을 받는다 |
| `BEFORE UPDATE/DELETE → SIGNAL` (V6) | 원장 변조. DB 가 거부한다(앱 관행이 아니라 제약) |

앱이 몇 대든 스레드가 몇 개든 같은 보장이 선다.

## 3. 회수 — 죽는 방식마다 다른 장치

`DeadJobRecoveryTask` 가 5초마다 세 단계를 돈다.

| 판정 | 조건 | 걸리는 시간 |
|---|---|---|
| heartbeat 만료 | ZSET score 지남 | 약 10~15초 |
| 정체(backstop) | `updatedAt < now − 60초`, heartbeat 없음/불명 | 약 60~65초 |
| **절대 상한** | heartbeat 가 **살아 있어도** `updatedAt < now − 300초` | 약 300초 |

세 번째가 없으면 **hang 인 워커의 종지기가 영원히 갱신해 돈이 영구히 묶인다.**
재시도는 지수 backoff(10초·40초), 상한 3회, 소진하면 전액 환불.

## 5. 결함 셋 — 원인이 하나다

### (1) 커넥션 풀을 전부가 나눠 쓴다

접수·워커·회수·대사·스냅샷이 **Hikari 10개**를 공유한다. 부하가 걸리면:

- **관측이 먼저 죽는다** — 게이지가 적체를 18,890 이라 말할 때 DB 실제값은 **140,424**(7.4배),
  게이지 신선도 **407초**. 스냅샷 태스크가 커넥션을 못 잡는다.
- **워커가 굶는다** — 10분 부하에 2,120건만 처리. 슬롯을 50개로 늘려도 **43~49개가 내내 비었다**
  (디스패처도 선점하려면 커넥션이 필요하다). 접수는 오히려 21% 느려졌다.
- **외부 실패의 뒷정리가 접수를 민다** — 외부 실패율 0.3 에서 접수 p99 +70%.

→ 세 증상이 한 원인이다. **풀을 용도별로 나누는 것이 첫 번째 할 일**이고, 효과는 아직 미측정이다.

### (2) 백프레셔가 없다

3,000 RPS 를 요구해도 **5xx 0건·성공률 100%**로 전부 받고 6초 기다리게 한다.
서버 지표는 건강해 보이는데 사용자는 이미 타임아웃이다. **성공률이 건강 지표로서 쓸모를 잃는다.**
거절해도 안전하다는 것은 측정됐다 — 일부러 5xx 를 4.2만 건 냈을 때 중복 차감이 0이었다.

### (3) hang 이 슬롯을 돌려주지 않는다

절대 상한이 돈은 풀지만 스레드는 영영 묶인다. 슬롯이 다 차면 **뒤에 줄 선 job 은 상한이 없다.**
인터럽트를 보내려면 `Future` 를 들고 있어야 하는데 지금은 `execute` 가 버린다.

## 6. 5.4초의 정체 — 인과를 한 번 정정했다

처음엔 "커넥션 대기열 190개가 5.4초를 만든다"고 적었다. **틀렸다.**
Hikari 획득 시간을 직접 재니 평균 **104ms**, 최대 1.63초, 타임아웃 0 — 5.4초의 2%다.

```
DB 트랜잭션 ≈ 10.4ms × 커넥션 10 = 초당 약 960 요청
→ 톰캣 스레드 200개가 그 처리율에 묶인다
→ 나머지는 accept 큐에서 대기  ← 5.4초의 대부분
```

**병목은 DB 처리율이고 커넥션 풀은 통로다.** 이 정정이 처방을 바꾼다 — 풀만 늘려도 소용없다.
실제로 워커 동시성을 3→50 으로 올려 DB 접근을 늘렸더니 접수가 **257 → 203 RPS 로 느려졌다.**

## 7. 대사 배치 — 규모에서 멈췄고, 고쳤다

원장 1억 행에서 대사 쿼리가 **265초 지나도 끝나지 않았고**, 그동안 같은 DB 를 쓰는 조회 API 의
p99 가 10ms → **8,489ms** 가 됐다. 원인은 `LIMIT 100` 이 `GROUP BY` **뒤에** 걸리는 것 —
100명을 얻으려고 1억 행 전부를 집계한다. 커서가 줄이는 것은 출력이지 스캔이 아니다.

**두 단계로 쪼갰다**: 사용자 id 100개를 먼저 확정(집계 없음 → `LIMIT` 이 스캔을 끊는다) →
그 100명의 원장만 집계. 동작은 같고 테스트 350건이 그대로 통과한다. **개선 폭은 미측정.**

부수 확인: 인덱스는 충분하다. `idx_ledger_user_id (user_id)` 단일 컬럼으로
`Backward index scan`(filesort 없음) — InnoDB 가 PK 를 접미로 갖기 때문이다.
**복합 인덱스도, 이 이유로는 파티셔닝도 필요 없다.**

## 9. 배포 전 확인 — 막는 것부터

- [ ] **운영 DB 에 `log_bin_trust_function_creators=1`** — 없으면 V6 마이그레이션이
      `ERROR 1419` 로 실패해 **배포가 멈춘다**(실행으로 확인함)
- [ ] 예상 피크가 **150 RPS 이하**인가
- [ ] 대사 주기(60초)가 원장 규모에서 한 주기 안에 끝나는가
- [ ] 경보: `snapshot staleness > 45초`(이게 울리면 다른 게이지는 전부 무효),
      `hikari pending > 20`, `접수 p99 > 100ms`
- [ ] 경보로 **쓰지 않을 것**: p50 · 평균 · 성공률

## 11. 규율

- 재지 않은 것은 **미측정**이라고 쓴다. 판정은 통과·실패·미측정 셋뿐이고 "예상 통과"는 없다.
- 실패를 지우지 않는다. 하나도 없으면 목표가 느슨했다는 뜻이다.
- 이 요구서는 **구현 이후 정식화(retrofit)** 됐다. 감추면 그 뒤의 모든 숫자가 의심받는다.
- 코드와 문서가 어긋나면 **코드가 맞다.**
