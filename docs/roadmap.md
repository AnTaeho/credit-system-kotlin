# 크레딧 시스템 로드맵 — 실제로 쓰는 서비스로

> 작성일: 2026-09-10 (v2) · 2026-09-19 (v3, 실서비스 전환 · v4, 단계 순서를 "먼저 한 바퀴"로)
> 목표: 내가 실제로 쓰는 개인 서비스로 만든다. 원화로 앱 내 크레딧을 충전하고(mock 결제),
> 크레딧을 써서 요청하면 이 서비스가 Claude API를 호출해 결과를 돌려준다. 앱 크레딧은 동전 세탁기의 동전이다.

> 제공할 기능은 아직 정하지 않았다. 이 문서는 기능과 무관하게 정해야 하는 정책과 그 구현 순서를 다룬다.

## 1. 방향

**"제품 하나가 성장한 기록"을 만든다.** 새 프로젝트를 만들지 않는다.
방어 코드(조건부 UPDATE·멱등키·attemptNo CAS·회수·관측)는 전부 그대로 가져간다.

**먼저 한 바퀴를 돌리고, 그다음 두껍게 만든다(결정 16).** 인터넷에 떠서 내가 실제로 쓰는 시점을 최대한 앞당기고,
원장 재설계처럼 큰 변경은 운영 데이터 위에서 마이그레이션으로 한다.

순서를 묶는 제약은 네 개뿐이다.
1. 인증 없이 인터넷에 올리지 않는다 → 인증이 배포보다 먼저
2. 타임아웃·멈춘 워커 대책 없이 진짜 Claude를 붙이지 않는다 → 외부 호출 안전화가 Claude 연결보다 먼저
3. 원가 상한과 일일 원가 차단기 없이 진짜 Claude를 붙이지 않는다 → 같은 단계에서 함께
4. 충전(CHARGE 원장 행)은 새 원장 구조 위에 만든다 → 원장 재설계가 PG보다 먼저

## 2. 확정된 설계 결정

### 결정 1 — Kafka를 넣지 않는다 (2026-09-10)
DB가 큐이고 상태 전이가 attemptNo CAS로 보호된다. 큐가 없어도 이중 처리가 안 난다는 게 step4~5의 논지다.
(v3: 서버를 1대만 운영하기로 해서(결정 13) 2대 실측으로 근거를 보강하는 계획은 빠졌다.)

### 결정 2 — 원장이 유일한 진실이다 (2026-09-10)
`initialBalance`를 없애고 초기 잔액도 CHARGE 원장 행으로 만든다. 대사 공식은 `잔액 − Σ원장`이 된다.
정산·대사 배치는 예외 없이 원장만 읽는다.

### 결정 3 — available / held 분리
```
hold:    available -= amount,  held += amount     WHERE available >= amount
confirm: held -= amount                            WHERE held >= amount
refund:  held -= amount,  available += amount      WHERE held >= amount
```
`held >= amount`는 이중 confirm을 막는 조건이 아니다(그건 attemptNo CAS가 한다).
훼손이나 버그로 held가 모자랄 때 조용히 음수가 되는 대신 0행을 돌려 방어 카운터에 잡히게 하는 조건이다.
total은 저장하지 않는다. 파생값이다.

### 결정 4 — 복식부기 원장 (2026-09-10, v3에서 부분 확정 제외)
행마다 from/to 계정을 가진다. 소비 계정과 충전 원천 계정은 사용자 행의 컬럼이 아니라 원장에만 존재하는 시스템 계정이다.
정정은 역분개 행 추가.
**v3 변경:** 고정가를 택해서(결정 10) confirm은 항상 hold 금액 전액이다. 부분 확정(`hold 100 → confirm 73 + refund 27`)은 만들지 않는다.

### 결정 5 — 감시 불변식
```
① available drift = available − Σ(to=available) + Σ(from=available)      항상 0
② held drift      = held      − Σ(to=held)      + Σ(from=held)           항상 0
③ held            = Σ(HOLDING·PROCESSING·FAILED 상태 job의 hold 금액)     상태-금액 일치
```
FAILED가 들어가는 이유: 이 코드는 FAILED 뒤에 REFUNDED가 따로 있어, FAILED인 job은 아직 held에 돈이 남아 있다.

### 결정 9 — 공개 인터넷, 실사용자는 나 혼자 (2026-09-19)
서비스는 인터넷에 떠 있지만 실제로 쓰는 사람은 운영자 한 명이다. 다른 사람은 쓸 수 없게 막는다.
**위협 모델:** 막을 대상은 "다른 사용자"가 아니라 **"선결제한 Claude 크레딧을 태우려는 낯선 사람"**과 **"나 자신의 실수(무한 루프·자동화 버그)"**다.
- 인증: **구글 로그인(OAuth2/OIDC) + 이메일 허용 목록.** 비밀번호를 저장하지 않는다. 허용 목록 밖이면 로그인 자체를 거부한다
- 익명으로 통하는 API는 없다(헬스체크·메트릭은 외부에 노출하지 않는다)
- ~~요청 속도 제한(rate limit)~~ — step9 에서 넣었다가 뺐다(2026-09-20). 총량은 잔액이, AI 호출 동시성은 워커 수가 이미 막는다. 이 위협을 실제로 막는 벽은 아래 일일 전체 원가 상한이다
- 일일 전체 원가 상한(결정 12)

### 결정 10 — 기능별 고정가, 작업 하나 = 100크레딧이 기준점 (2026-09-19)
- 가격은 `(기능, 규모 등급) → 크레딧` 표로 둔다. 예: 소·중·대 = 60·100·200
- 가격표는 버전을 가진다. job은 접수 시점의 **가격(과 모델·원가 상한)을 스냅샷**한다. 가격을 바꿔도 진행 중인 job은 흔들리지 않는다
- **크레딧 한 개의 원화 가치는 아직 정하지 않는다.** 기능이 정해진 뒤 job별 실제 원가 데이터(결정 11)로 산출한다
- 회계 단위는 정수 `Long`이다. 소수점 크레딧은 없다

### 결정 11 — Claude API, 원가 상한 강제와 원가 기록 (2026-09-19)
- 외부 AI는 **Claude API**다. Kotlin에서는 공식 Java SDK(`com.anthropic`)를 쓴다. 기능별 모델은 가격표에 포함한다
- **고정가의 짝: 최악의 원가 ≤ 가격.** 기능마다 입력 길이 상한과 `max_tokens`를 강제해서
  `입력 상한 × 입력 단가 + max_tokens × 출력 단가`가 그 기능 가격의 원화 가치를 넘지 못하게 한다. 이 식은 가격표 등록 시 검증한다
- **job마다 실제 원가를 기록한다.** 응답의 `usage`(입력·출력·캐시 토큰)와 그 시점 단가로 USD 원가를 계산해 저장한다.
  응답을 못 받은 실패(타임아웃 등)는 원가를 알 수 없으므로 **상한값으로 추정**하고 추정임을 표시한다
- **SDK 기본값을 그대로 쓰지 않는다.** SDK는 기본 타임아웃 10분, 자체 재시도 2회(408/409/429/5xx)를 가진다.
  우리에겐 attemptNo 재시도가 이미 있어서 둘을 겹치면 원가가 곱으로 늘고 벽시계 시간이 `timeout × 3`이 된다. 타임아웃은 기능별로 짧게 잡고 SDK 재시도는 끈다(또는 한 곳에서만 재시도한다)
- `stop_reason`이 `refusal`이면 실패로 보고 환불한다. `max_tokens`에 걸려 잘린 결과를 성공으로 볼지는 기능별로 정한다(미결)

### 결정 12 — 실패는 전액 환불, 손실은 운영자가 떠안고 지표로 본다 (2026-09-19)
- 외부 호출이 실패하면 사용자에게 전액 환불한다(지금 환불 흐름 그대로). 재시도로 원가가 여러 번 나가도 사용자는 한 번만 낸다
- Claude API에는 멱등키가 없다. 타임아웃이 난 요청도 저쪽에서는 처리·과금됐을 수 있다. 이 원가는 운영자 손실이다
- 원가 손실을 지표로 만든다: `원가(성공) · 원가(실패·추정) · 매출(크레딧) · 마진`
- 원가 보호 장치:
  - **일일 전체 원가 상한(비상 차단기).** 오늘의 실제 원가가 상한을 넘으면 새 접수를 거절하고 알람을 울린다. 인증이 뚫려도 피해가 하루치로 묶인다
  - ~~**요청 속도 제한.** 사용자별 분당 접수 수~~ — step9-D 로 넣었다가 같은 단계에서 뺐다(2026-09-20). 총량은 잔액, 동시성은 워커 수가 막으므로 남는 효용이 "총량이 아니라 속도" 하나뿐이었고, 그 값어치가 유지 비용보다 작다고 봤다. 피해를 묶는 역할은 위의 일일 전체 원가 상한이 전부 진다
  - Claude 쪽 402/429를 감지해 접수를 자동으로 멈추는 장치는 **넣지 않는다.** 선결제 잔고가 바닥나면 요청마다 실패하고 환불된다. 돈은 안전하고, 계기판과 원가 상한 알람으로 알아챈다

### 결정 13 — 서버는 1대 (2026-09-19)
실사용자가 한 명이라 2대를 띄울 이유가 없다. 스케줄러 겹침 실측과 ShedLock은 하지 않는다.

### 결정 14 — 충전은 실제 PG 모양의 mock, 고정 패키지 (2026-09-19)
- 실제 돈은 받지 않는다. 하지만 흐름은 실제 PG(토스페이먼츠 같은)를 흉내 낸다: **결제 준비 → 승인 → 웹훅**
- 방어할 실패: 중복 웹훅, 승인 성공 후 콜백 유실, 금액 위변조(서버가 가진 준비 금액과 대조), 승인 지연
- 패키지는 5천·1만·3만원 고정. 원화 → 크레딧 환산표는 한 곳에 둔다(결정 10의 단가가 정해지면 채운다)
- mock PG는 별도 모듈로 두고 인터페이스를 실제 PG와 같은 모양으로 만든다. 나중에 실제 PG로 갈아끼울 수 있게
- 기존 `POST /me/charge`는 step9에서 막고(운영자 전용 충전만 남김) step14에서 이 흐름으로 교체한다

- 크레딧 유효기간 없음. 충전분 원화 환불 없음(mock 결제라 의미 없음). 원장에는 기록만 한다

### 결정 16 — 먼저 한 바퀴, 그다음 두껍게 (2026-09-19, v4)
v3는 원장 → 인증 → Claude → PG → 배포 순이라 마지막 단계가 끝나기 전에는 서비스를 한 번도 쓸 수 없었다.
v4는 인증 → 배포 → 외부 호출 안전화 → Claude·원가 → 원장 → PG 순으로 바꿔 step12부터 실제로 쓴다.
- **얻는 것:** 실사용 시점이 앞당겨지고, 원가 데이터가 일찍 쌓여 크레딧 단가(결정 10)를 빨리 정한다. 인프라 문제가 일찍 드러난다. 단계가 작아진다
- **치르는 값:** 원장 재설계를 운영 데이터 위에서 한다. 백업 → 리허설(운영 덤프 복제본에 먼저 적용) → 적용 → drift 0 확인 절차가 필수다. step13 전까지는 단식 원장으로 운영하지만 방어 코드와 대사가 돌고 있다
- v2의 "옛 스키마를 VM에 올렸다가 다시 올리지 않기 위해 원장 먼저"라는 근거는 Flyway 도입(step8)과 단일 사용자·mock 돈이라는 조건에서 약해졌다

- 구글 로그인은 Spring Security `oauth2Login` + 세션. 브라우저에 토큰을 보관하지 않는다

### step10 — 배포 1대

**증명하는 것:** 인터넷에 떠 있고, 배포해도 처리 중이던 job이 회수가 아니라 드레인으로 끝나며, 알람이 나에게 온다.
**규모:** 중간. 인프라 삽질 시간이 예측이 안 되니 넉넉히.

1. VM 1대(Oracle Cloud Always Free ARM 후보). compose로 app + MySQL + Redis + Prometheus + Grafana + Alertmanager + Caddy(TLS). 도메인
2. CD: GHCR push 뒤 SSH로 `compose pull && compose up`
3. graceful shutdown: `step8-b-drain-archive`의 드레인 구현을 살린다. 대기 상한은 `processing.timeout`에서 유도
4. Alertmanager → Discord(또는 이메일). 불변식·회수 알람이 실제로 도착하는지 확인
5. 비밀: 구글 OAuth 클라이언트 비밀, DB 비밀번호(이후 Claude API 키)를 환경변수·파일로. 저장소에 없다
6. health 재설계: Redis down이 readiness DOWN이 되면 안 된다(백스톱이 있으니 degraded). liveness와 readiness 분리
7. 백업: MySQL 정기 덤프와 **복구 리허설**. step13의 운영 데이터 마이그레이션이 이 백업에 기댄다

**완료 기준:** `develop` 머지 후 손대지 않아도 VM이 새 버전으로 바뀐다. 배포 중 처리 중이던 job이 회수 없이 완료된다. 알람이 휴대폰에 도착한다. 덤프에서 복구한 DB로 앱이 뜬다.

### step11 — 외부 호출 안전화

**증명하는 것:** 외부 생성이 느리거나 죽거나 **영원히 응답하지 않아도** 돈이 묶이지 않고 워커 자리가 사라지지 않는다.
**규모:** 중간. 진짜 Claude를 붙이기 전의 준비 단계라 가짜 생성기로 전부 실측한다.

1. `GenerationClient` 인터페이스 분리. 가짜 생성기에 지연·실패·무응답(hang)을 설정으로 주입
2. 외부 호출 타임아웃. 재시도는 attemptNo 한 곳에서만(결정 11)
3. 멈춘 워커 구멍: heartbeat 수명 상한 또는 백스톱 절대 상한(LIVE여도 아주 오래된 PROCESSING은 회수). attemptNo CAS가 오회수에서 돈을 지킨다
4. 재시도 backoff: 회수 직후 바로 HOLDING이 아니라 `다음 시도 가능 시각`을 둔다
5. 요청 상관 ID(MDC)와 JSON 구조화 로그. job이 HTTP → 워커 → 외부 호출을 거쳐도 같은 ID
6. 장애 시나리오: 무응답·연속 실패·지연 폭증을 재현해 회수·환불·워커 슬롯 복귀를 실측

**완료 기준:** 가짜 생성기가 영원히 응답하지 않아도 job이 상한 시간 안에 FAILED → 환불되고, 워커 빈 자리가 원래대로 돌아온다.

### step12 — 진짜 Claude와 원가

**증명하는 것:** 원가가 가격을 넘지 않고, 선결제 잔고가 하루 상한 이상 빠지지 않으며, 내가 실제로 쓴다.
**규모:** 크다. 이 서비스의 본체가 붙는 단계.

1. Claude 구현(공식 Java SDK `com.anthropic`). prod는 Claude, 테스트·로컬은 가짜. SDK 자체 재시도는 끄고 타임아웃은 기능별로(결정 11)
2. 가격표(결정 10): `(기능, 등급) → 크레딧·모델·입력 상한·max_tokens`, 버전 관리, 등록 시 "최악 원가 ≤ 가격" 검증. job에 스냅샷
3. job별 원가 기록(결정 11): usage 토큰, USD 원가, 추정 여부. `refusal`은 실패로 보고 환불
4. 일일 전체 원가 상한 차단기와 알람(결정 12). 원가·매출·마진·손실 지표와 대시보드
5. **첫 실제 기능.** 이 단계 착수 전에 기능을 정한다. 결과 보관 기간·위치도 함께
6. 크레딧 한 개의 원화 가치: 첫 주 실사용 원가 데이터로 1차 산출(결정 10)

**완료 기준:** 원가 상한을 넘기는 가격표 행은 등록이 거부된다. 일일 원가 상한을 넘으면 새 접수가 거절되고 알람이 뜬다. 첫 기능을 실제로 쓰고, 그 job들의 원가·마진이 계기판에 보인다.

### step13 — 원장 재설계 (운영 데이터 위에서)

**증명하는 것:** 복식부기 원장으로 "돈이 어디서 어디로 갔는지"가 빠짐없이 남고, 불변식 3개가 실측으로 0이다. 그 전환을 운영 데이터를 잃지 않고 해낸다.
**규모:** 크다. 가장 넓게 번지는 변경이고, 운영 중인 DB에 적용한다.

1. Flyway: `users`에 `available`·`held` 추가, 기존 잔액과 원장 이력 → CHARGE·운영자 지급 행으로 이관, `balance` 제거. `ledger_entries`에 `from_account`·`to_account`
2. 사용자 잔액 hold/confirm/refund 3쿼리(결정 3). 각 0행 분기가 `DefenseMetrics` point 라벨
3. `LedgerEntry` 복식 전환(결정 4). CONFIRM이 실제 금액을 가진다(항상 hold 전액)
4. 대사 태스크: drift 공식을 계정별로 분리(결정 5). 스냅샷 게이지: held 실측 vs Σ job 비교
5. 알람·대시보드 갱신(`CreditNegativeBalanceOrgs` → available·held 둘 다). 원장과 관련된 장애 시나리오(05 등)만 재실측
6. **운영 적용 절차:** 백업 → 운영 덤프 복제본에 리허설 → 접수 일시 중지와 드레인 → 적용 → drift 0 확인 → 재개. 되돌리기 절차를 먼저 쓴다
7. 문서 `docs/step13-ledger.md`에 "왜 바꿨나", 이관 규칙, 운영 적용 기록

**완료 기준:** 기존 테스트 통과(잔액 관련은 재작성). 시나리오 05에서 훼손이 available drift·held drift 중 어느 쪽인지 구분되어 알람이 뜬다. 운영 DB 전환 후 drift 0, 이관 전후 잔액 합계 일치.

### step14 — mock PG 충전

**증명하는 것:** 결제 흐름의 실패(중복 웹훅·콜백 유실·금액 위변조)에서도 크레딧이 한 번만, 정확한 금액으로 생긴다.
**규모:** 중간.

1. mock PG 모듈: 결제 준비(주문 id·금액 발급) → 승인 → 웹훅. 지연·중복 전송·유실을 설정으로 재현(결정 14)
2. 결제 주문 테이블과 상태 전이(준비 → 승인 → 충전 완료). 조건부 UPDATE와 멱등으로 이중 충전 방지
3. 웹훅 서명 검증과 금액 대조. 콜백 유실 대비 주기적 조회(결제 상태 대사)
4. 원장: CHARGE 행은 `충전 원천 → available`. 패키지(5천·1만·3만원)와 원화 → 크레딧 환산표(step12의 단가 반영)
5. 화면: 패키지 선택 → mock 결제 → 잔액 반영. 운영자 전용 충전 경로는 이때 닫는다

**완료 기준:** 같은 웹훅이 3번 와도 크레딧은 1번 생긴다. 웹훅이 유실돼도 대사가 충전을 완료한다. 원장 drift 0.

### 뺀 것 (v2에 있던 단계)

- **옛 step10의 2대 무중단 배포, ShedLock, k6 상시 트래픽:** 서버 1대(결정 13)
- **옛 step11의 OpenAPI, Resilience4j 서킷브레이커·벌크헤드, OpenTelemetry:** 필요해지면 다시 본다. 타임아웃·재시도·상관 ID는 step11로 옮겼다
- **옛 step12 대용량과 정산(수천만 행 생성기, Spring Batch 월 정산서):** 사용자 한 명의 서비스에서는 증명할 대상이 없다

## 5. 면접 관통 질문

- **왜 큐를 안 썼나** — DB가 큐, CAS가 보호. 서버 1대라 겹칠 소비자도 없다
- **운영 중인 원장 구조를 어떻게 바꿨나** — step13. 백업·리허설·드레인·적용·drift 0 확인, 되돌리기 절차 선작성
- **배포 중 처리 중이던 job은** — graceful shutdown(step10)이 정상 경로, 회수(step5)는 안전망
- **외부 AI가 멈추면** — 타임아웃이 hang을 예외로 바꾸고, 백스톱 상한이 마지막 그물. 사용자는 환불, 원가는 손실 지표로
- **고정가인데 원가가 튀면** — 기능마다 입력 상한과 max_tokens로 최악 원가를 가격 아래로 묶고, 등록 시 검증한다
- **인증이 뚫리면** — 피해 상한은 일일 원가 상한. 사용자 크레딧과 별개인 두 번째 벽
- **결제 웹훅이 두 번 오면** — 결제 주문 상태의 조건부 UPDATE. 크레딧은 한 번만 생긴다
- **조건부 UPDATE의 한계** — 사용자당 한 행이라 hot row. 사용자 한 명이면 문제가 안 되지만, 늘면 버킷 분할 검토
- **성능 수치 재현 조건** — 모든 수치에 하드웨어·데이터 규모·풀 크기·도구 명시

## 6. 원칙

- 관측·과금·원가·충전·배포는 전부 크레딧 시스템 안에 편입한다
- 돈이 움직이는 모든 곳에 조건부 UPDATE와 원장 행. 예외는 없다
- 모든 수치에 재현 조건. 한계는 먼저 밝힌다
- 도메인 개념 하나당 설계 변경 하나
- 판단 지점은 임의 결정하지 않고 기록한다
- 리팩터링은 코드가 덜 알게 만드는 것. 파일·패키지 수는 근거가 아니다
