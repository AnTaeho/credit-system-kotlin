# 2026-09-23 — PERF-04 원장 1억 행에서의 조회

## 한 줄

**조회 자체는 통과한다(p99 10~13ms). 그러나 운영 조건에서는 같은 DB 를 쓰는 대사 배치가
조회를 3.7초로 만든다.** 인덱스는 충분하고, 문제는 배치 쿼리의 모양이다.

## 판정

| 조건 | 첫 페이지 p99 | 다음 페이지 p99 | 판정 |
|---|---:|---:|---|
| **워밍 상태 · 스케줄러 꺼짐** | **10.13ms** | **12.68ms** | **통과** (목표 50ms) |
| 콜드 상태(재시작 직후) · 스케줄러 꺼짐 | 193.10ms | 24.70ms | 실패 |
| **워밍 상태 · 스케줄러 켜짐(운영 기본값)** | **8,489ms** | **14,045ms** | **실패 — 170~280배** |

세 줄이 같은 시스템의 같은 엔드포인트다. 달라진 것은 캐시 상태와 **대사 배치가 도는지**뿐이다.

## 적재 — 조회보다 쓰기가 먼저 막힌다

1,000명(사용자당 1만 행)이 아니라 **10,000명 × 5,000쌍 = 1억 행**으로 만들었다.
사용자당 행 수를 1만으로 고정해 테이블 크기 효과만 남겼다.

| 버퍼 풀 | 삽입 속도 | 비고 |
|---|---:|---|
| 128MiB (고정값) | 263k → 76k → 35k → **21k 행/초** | 계속 붕괴. 640만 행에서 중단 |
| 1.5GiB (적재 전용 임시) | 192k → **101k 행/초** (평균) | 1억 행 992초 |

분산 삽입은 `user_id` 가 흩어져 **세컨더리 인덱스에 랜덤 쓰기**를 만든다. 인덱스가 버퍼 풀을
벗어나는 순간 삽입이 무너진다. 고정값 128MiB 로는 1억 행 적재 자체가 현실적이지 않았다.

**그래서 적재 단계만 버퍼 풀을 1.5GiB 로 올리고, 측정 전에 다시 128MiB 로 되돌린 뒤
컨테이너를 재시작해 콜드 상태에서 쟀다.** 적재 편의가 측정에 섞이지 않게 한 것이다.

최종 크기: 데이터 **5,335MiB** + 인덱스 **5,148MiB** = 약 10.5GiB. 버퍼 풀의 **80배**다.

## 인덱스 — 단일 컬럼으로 충분하다

설계 문서(`docs/02-design.md`)가 "`EXPLAIN` 전에는 단정할 수 없다"고 남긴 질문의 답이다.

```
첫 페이지:  WHERE user_id = ? ORDER BY id DESC LIMIT 20
  key: idx_ledger_user_id      Extra: Backward index scan       ← filesort 없음
```

InnoDB 세컨더리 인덱스는 PK 를 접미로 갖는다. 그래서 `(user_id)` 한 컬럼만으로
`ORDER BY id DESC` 까지 인덱스가 해결한다. **복합 인덱스 `(user_id, id)` 를 추가할 이유가 없다.**

다만 커서 다음 페이지는 경로가 다르다.

```
다음 페이지: WHERE user_id = ? AND id < ? ORDER BY id DESC LIMIT 20
  key: idx_ledger_user_id,PRIMARY
  Extra: Using intersect(idx_ledger_user_id,PRIMARY); Using where; Using filesort
```

옵티마이저가 두 인덱스의 교집합을 고르고 **filesort** 가 붙는다. 그런데 실측은 첫 페이지와
비슷하다(워밍 p99 12.68ms vs 10.13ms) — 교집합 뒤 남는 행이 적어 정렬 비용이 작기 때문이다.
**계획이 나빠 보여도 실측이 그것을 부정한 자리**다.

### 시드 방식이 결론을 뒤집을 뻔했다

처음에는 `seed-ledger.sh` 로 **한 사용자에게** 1천만 행을 넣고 쟀다. 그때 옵티마이저는
세컨더리 인덱스를 쓰지 않고 **PRIMARY 역방향 스캔**을 골랐고 1.27ms 가 나왔다.
그 사용자가 사실상 모든 행을 가져서 id 를 역순으로 훑기만 하면 바로 맞는 행이 나오기 때문이다.

이 값을 그대로 적었다면 "PK 로 충분하다"는 **틀린 결론**이 됐을 것이다.
실제 서비스에서는 한 사용자가 전체의 극히 일부만 갖는다. 분산 시드
(`load/seed/seed-ledger-spread.sh`)로 바꾸고 나서야 진짜 인덱스 경로가 나왔다.

| 시드 방식 | 1천만 행에서 고른 인덱스 | 평균 |
|---|---|---:|
| 한 사용자가 전부 소유 | PRIMARY 역방향 스캔 | 1.27ms |
| 1,000명에 분산 | `idx_ledger_user_id` 역방향 스캔 | 0.45ms |

## SQL 직접 측정 (참고)

`load/measure-ledger-read.sh` 로 앱을 거치지 않고 잰 값이다.

| 원장 행 수 | 커서 페이지 평균 |
|---:|---:|
| 1천만 (분산) | 0.451ms |
| **1억 (분산, 콜드)** | **0.521ms** |

**행이 10배로 늘어도 0.45 → 0.52ms.** B-트리 조회라 테이블 크기에 로그로만 반응한다.
API 값(p99 10~13ms)과의 차이는 인증 트랜잭션·JPA·직렬화·HTTP 다.

## 진짜 병목 — 대사 배치가 조회를 죽인다

스케줄러를 켠 상태(운영 기본값)에서 잰 첫 측정이 p99 **8,489ms** 였다.
그때 DB 의 프로세스 목록을 보니 대사 쿼리가 **265초째 실행 중**이었고, 한 번도 완료되지 않았다
(앱 로그의 "원장 대사 주기 완료" 0건).

```sql
select u.id, u.balance, u.initial_balance, coalesce(sum(l.amount),0)
from users u left join ledger_entries l on l.user_id = u.id
where u.id > 0
group by u.id, u.balance, u.initial_balance
order by u.id limit 100
```

`EXPLAIN` 은 `Using temporary; Using filesort` 를 붙인다.

**`LIMIT 100` 이 `GROUP BY` 뒤에 걸린다.** 즉 100명을 얻으려고 **1억 행 전부를 조인·집계한 뒤**
100행만 남긴다. 커서(`where u.id > ?`)가 붙어 있어 페이징처럼 보이지만, 그것이 줄이는 것은
**출력이지 스캔이 아니다.** 사용자가 늘수록 매 배치가 같은 전체 집계를 반복한다.

| 원장 행 수 | 대사 1주기 |
|---:|---|
| 200만 | 1.18초 |
| 1,000만 | 120초 초과 (측정 중단) |
| **1억** | **265초 지나도 미완료** |

`app.scheduling.reconciliation-interval-millis` 는 60000(60초)이다. **한 주기가 간격보다
오래 걸린다.** `fixedDelay` 라 겹치지는 않지만, DB 는 사실상 쉬지 않고 이 쿼리를 돈다.

## 결론

| 질문 | 답 |
|---|---|
| 인덱스가 부족한가 | **아니다.** 단일 컬럼 `(user_id)` 로 충분하다(PK 접미 덕분) |
| 조회가 1억 행에서 느려지는가 | **아니다.** SQL 0.52ms, API p99 10~13ms |
| 그럼 PERF-04 는 통과인가 | **운영 조건에서는 실패한다.** 대사 배치가 같은 DB 를 점유해 p99 8.5초 |
| 무엇을 고쳐야 하나 | 조회도 인덱스도 아니고 **대사 쿼리의 모양**이다 |

### 대사 쿼리를 고치는 방향 (미검증)

- 사용자 구간을 **먼저 자르고** 그 구간만 집계한다 —
  `WHERE u.id > ? AND u.id <= ?` 로 100명을 확정한 뒤 그 100명의 원장만 합산.
  지금은 전체를 집계한 뒤 100명을 고른다.
- 또는 사용자별 합계를 증분 유지하고 대사는 그 값과 비교만 한다.
- 어느 쪽이든 **재기 전에는 모른다** — 이 문서는 현재 쿼리가 1억 행에서 끝나지 않는다는 사실까지다.
