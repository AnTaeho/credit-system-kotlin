# 2026-09-23 — 01 Tier A 정상 부하 (PERF-01 · 02 · 07)

## 한 줄

**접수 500 RPS 목표에 257 RPS 로 미달했고 지연은 목표의 130~270배였다. 그러나 15만 4천 건의
차감이 일어나는 동안 원장은 한 건도 어긋나지 않았다.** 먼저 포화된 것은 DB CPU 와 커넥션 풀이고,
앱 CPU 는 남았다.

## 부하 모델과 실제 달성치

| | 목표 | 실측 | 비고 |
|---|---:|---:|---|
| 쓰기(접수) | 500 RPS × 600초 = 300,000 | **154,383 (257 RPS)** | 51% |
| 조회 | 1,500 RPS = 900,000 | **463,293 (772 RPS)** | 51% |
| `dropped_iterations` | 0 | **582,327** | 목표 도달률 51% |
| VU 최대 | — | 6,000 (상한) | |

**`dropped_iterations` 가 0 이 아니므로 이 런은 "500 RPS 에서의 지연"이 아니라
"500 RPS 를 요구했을 때 이 시스템이 낸 257 RPS 와 그때의 지연"이다.**
k6 자체의 한계는 아니다 — 응답이 5~12초씩 걸려 VU 6,000 개가 전부 대기에 묶였고,
도착률 실행기가 새 반복을 띄우지 못해 버린 것이다. 즉 이 수치는 시스템의 결과다.

## 무엇이 먼저 포화됐나

| 시각 | MySQL CPU (상한 400%) | 앱 CPU (상한 400%) | Hikari active / pending |
|---|---:|---:|---|
| 14:09 | 220% | 120% | 10 / **190** |
| 14:10 | **410%** | 56% | 10 / **191** |
| 14:11 | **407%** | 31% | 10 / **192** |
| 14:12 | 261% | 103% | 9 / **193** |
| 14:13~14:17 | 209~339% | 40~118% | 10 / **191~192** |

**순서: ① HikariCP 커넥션 10개 포화 → ② MySQL CPU 가 제 상한에 접촉 → ③ 앱 CPU 는 여유.**

커넥션 대기열이 첫 샘플부터 190 으로 차 있고 끝까지 그 값이다. 풀이 10 인데 대기가 190 이면
요청 하나가 커넥션을 얻기까지 평균 19 순번을 기다린다 — 관측된 p50 5.4초가 그 줄의 길이다.

## 관측이 먼저 죽는다 (이 런에서 가장 중요한 발견)

| 지표 | 값 |
|---|---:|
| 스냅샷 게이지 `credit_hold_outstanding_count` | 18,890 |
| **DB 에서 직접 센 HOLDING** | **140,424** (같은 시각) |
| `credit_snapshot_staleness_seconds` | **407초** |
| 스냅샷 1주기 평균 소요 | 6.4초 (`sum 134.8s ÷ 21 cycles`) |

게이지가 **7.4배 과소 보고**했다. 원인은 구조다 — `DomainSnapshotTask` 도 접수 요청과 **같은
Hikari 풀 10개**를 쓴다. 접수가 풀을 점유하면 스케줄러가 커넥션을 못 잡고, 잡아도 6.4초가 걸려
15초 주기를 지키지 못한다.

같은 이유로 **워커도 굶는다.** 부하 10분 동안 COMPLETED 는 2,120건뿐이었다.

**따라서 이 시스템은 부하에서 뒤처지기만 하는 것이 아니라, 자기 회복 장치(워커·회수)와
관측 장치(스냅샷)를 함께 굶긴다.** 계기판이 거짓말을 시작하는 지점이 바로 대응이 필요한 지점이다.

### ADR-004 의 공식이 재현됐다

JAVA 저장소 `develop-report.md`(2026-08-20)의 batch-size 실측이 세운 식:

```
처리량 상한 = min(concurrency / job소요시간, concurrency / 폴링주기)
```

이 런의 값을 넣으면 `min(3 / 0.05~0.1초, 3 / 0.5초) = min(30~60, 6.0) = 6.0건/초`.
**실측 5.85건/초.** 그 문서가 Java 에서 잰 천장 5.8 TPS 와 같은 값이다.

즉 스텁을 20~140배 빠르게 해도 처리량은 6/초에서 막힌다. **구속하는 항은 job 소요시간이 아니라
폴링 주기**이고, 그것을 바꾸지 않는 한 워커를 아무리 빠르게 해도 소용이 없다.
이는 ADR-002 가 산술로만 말했던 결론("전송 수단을 바꿔도 구속하는 항은 움직이지 않는다")의
실측 근거이기도 하다.

- **INV-03**: 5xx 가 한 건도 없어 재시도 경로가 타지 않았다. 멱등성은 이 런에서 미검증이다.
  04 생존 스파이크에서 검증된다.

## 함정 기록

1. **k6 가 abort 하면 데이터 0건인 채로 thresholds 가 전부 PASS 로 찍힌다.**
   첫 시도가 시드 부족으로 중단됐을 때 11개 항목이 모두 PASS 였다.
   결과를 읽을 때 `iterations` 와 `http_reqs` 가 0 이 아닌지 **반드시 함께** 봐야 한다.
2. **시드 선행 검사가 값어치를 했다.** 스텁 확인용으로 쓴 10건(1,000 크레딧) 때문에 정확히
   1,000 이 모자랐고 k6 가 부하 전에 멈췄다. 없었으면 부하 중반부터 409 가 쏟아지고
   그 실패가 시스템의 결과처럼 기록됐을 것이다.
3. **게이지를 믿고 적체를 적으면 7.4배 틀린다.** 부하 중 적체는 DB 에서 직접 세야 한다.
